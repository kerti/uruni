# ADR-012 — Backup & export implementation

**Status:** Accepted · `draft` — backup, restore and daily dumps are built (M6); Excel (parked 2026-10-07, unscheduled) and the full format upgrade chain (the `v1.0.0` gate) are not - its first step, `format_version` 1 to 2 ([ADR-040](./040-effective-dated-tiers-and-rate-corrections.md)), is, and `uruni rebuild` ([#516](https://github.com/kerti/uruni/issues/516), M9) is the `0.x` stopgap for schema-changing upgrades, so it may still be edited in place · [ADR index](./README.md)

**Decision.**
- **JSON export**: Go `encoding/json` serializes all tables into one **versioned** document; a matching **import** restores it.
- **The backup is one `.zip`** (stdlib `archive/zip`): `uruni.json` plus a `receipts/` folder holding every receipt image under its stored, server-generated name. Import restores both. The JSON's own `version` is the only version; the zip adds no manifest. This keeps [ADR-011](./011-receipt-photos-local-volume.md)'s "the export references photo files rather than embedding them": the JSON names each file, the file sits beside it. A JSON-only download would restore `receipt` rows pointing at images that no longer exist; base64 inside the JSON was rejected (a third larger, and one parse holds every photo in memory). *(Grill A, 2026-09-28.)*
- **The in-app restore is atomic** (Pengaturan, beside the download). It never swaps the database file (`uruni rebuild`, below, is the one path that does, onto a file it built itself): it replaces every row inside **one write transaction** on the already-open connection, so a bad file rolls back and a file swap's orphaned inode ([#278](https://github.com/kerti/uruni/issues/278)) cannot happen. The single connection (`SetMaxOpenConns(1)`, [ADR-004](./004-database-sqlite-only.md)) makes other requests wait for the commit, which is all a maintenance mode would have bought. Order: write a **safety-net backup** of the current state to the backup directory; extract receipt images into the uploads volume (additive; a name clash is the same file); then the row transaction. A restore that fails after extraction removes the images it created (not ones already on disk under the same name), so a refused restore leaves only the safety-net dump behind. The confirm step shows what the file holds (export date, funds, total) and asks for the password again - the treasurer's **current** password, not anything decoded out of the file; see "Login is not restored" below. Sessions are never exported, so a restore logs everyone out and forgets every idempotency key ([ADR-043](./043-idempotency-keys-on-immutable-writes.md)), both cleared in the same transaction: a key from before the restore would replay a success whose rows the restore has just removed. The upload gets its own caps (body, unzipped total, entry count), refuses a backup newer than the running binary, and every image passes the receipt decode checks. There is no `uruni import`: the CLI half of restore is `uruni rebuild`, which runs the same parse and the same row insert and totals proof over a fresh file ("`uruni rebuild`" below). The logic lives in one package, `internal/backup`, so both halves share it. *(Grill A, 2026-09-28; the import retired 2026-10-14, #516.)*
- **Restoring one of the server's own stored dumps reuses this exact path** ([#326](https://github.com/kerti/uruni/issues/326)). The Cadangan card's list already addresses each dump by a server-side filename (`GET /api/backups/{name}`, validated the same way a download is); restore adds a second inspect route over that same identifier, `POST /api/restore/inspect-stored/{name}`, which reads the named file out of the backup directory, decodes it through the very same `backup.ParseUpload`, and hands the result to the same preview-then-stage tail an uploaded file goes through - so an old-format dump is upgraded, or refused, by the same format-version check an old-format upload meets, not a second, separately-maintained one. `POST /api/restore/confirm` is unchanged: it takes a token and a password and does not know or care which inspect route staged what it is confirming. A dump is offered "pulihkan" in the UI when the importer can read it - the current format, or an older one it upgrades in `ParseUpload` (`backup.CanUpgradeFormat`) - which the list reports as `can_restore`; `is_current_format` stays the signal for the "older version" label, so the previous release's dump shows both. A safety-net dump from a previous restore is itself always current-format (it is built from the live `Document`, which is always exported in the running binary's own format), so it is restorable too - a restore can undo a restore. Both inspect routes stream their input into its own on-disk staging file under `URUNI_BACKUP_DIR` before `ParseUpload` ever runs (issue [#344](https://github.com/kerti/uruni/issues/344)), never holding the upload - or the stored dump being copied - fully in memory; confirm reads only that staged copy, so a stored-dump restore survives the original file being pruned by retention (including by the safety net this very restore is about to write) or deleted between inspect and confirm. Each inspect's file gets its own generated name rather than one shared slot, and only the in-process stage's own mutex - never a filesystem rename - decides which staged file a token names, so two concurrent inspects can never race over whose bytes a shared name ends up holding.
- **The backup holds every table except `session` and `idempotency_key`** (both are state of the running server, not of the fund) - `user` included, so the zip carries a password hash and every name; the download copy says to keep it somewhere safe. The report slug lives on `fund`, so a restore keeps the link the group already has. *(Grill A, 2026-09-28.)*
- **Excel**: generated server-side with **excelize** - human-readable, not the restore path. **Parked 2026-10-07** ([#328](https://github.com/kerti/uruni/issues/328)): unscheduled, and maybe never built. The design below stands if it is. `.xlsx`, not CSV: Indonesian-locale Excel splits lists on `;`, so a comma CSV opens with every field crammed into column A. **Mirror, don't compute**: each sheet shows only what a screen already derives - Ringkasan (balances per location and purpose, latest reconciliation), Transaksi (receipt present as yes/no), Anggota, Amplop, Talangan, Rekonsiliasi - each with a Dana column rather than a sheet per fund. Amounts are number cells with a rupiah number format, never text. Raw tier/rate tables, a separate transfer sheet and the images are left out. A member-by-month dues grid goes in only if the app already derives one by M8. *(Grill A, 2026-09-28.)*
- **Scheduled dumps**: once a day, in-process ([ADR-013](./013-scheduling-in-process.md)), `serve` writes the same backup zip to `URUNI_BACKUP_DIR` (default `./backups`, `/backups` in the container; boot-checked like `URUNI_UPLOADS_DIR`) - **only if the fund changed** since the last dump, judged by a hash of `uruni.json` plus the receipt file list, computed before any zip is built, so an unchanged day builds nothing ([#501](https://github.com/kerti/uruni/issues/501)). Dumps and receipt files are fsynced before their rename and the directory after it, so a power loss cannot leave a final name pointing at an empty file. So retention counts *versions*, not days: the last **7** daily dumps are kept, plus the last **3** safety-net backups from restore, in separate quotas. On by default with no switch - retention is bounded, so there is nothing to turn off for. The Pengaturan backup card lists them (date, kind) with download and restore; restoring from one runs the same atomic path as an upload, minus the upload. Dumps on the same disk do not survive losing the disk: off-site copies (e.g. syncing `URUNI_BACKUP_DIR` to object storage with rclone or restic) are a **self-host README recommendation**, never an app feature - what the operator does with their machine is outside the app. No download reminder in the app (PRD section 4: no reminders). *(Grill A, 2026-09-28.)*
  **The day and the name are the fund's** *([ADR-041](./041-the-funds-time-zone.md))*. "Does today have its dump" compares the dump's *instant* with the current instant, both read in the fund's time zone as it is now; the hourly tick is unchanged and reads the zone of the first `ListFunds` row on each tick (`tz.Default` before any fund exists, so the boot dump on a fresh instance is stamped in WIB). A dump's name is `uruni-<date>-<time>[-<token>]-<kind>-fv<n>-<hash12>.zip`, stamped in the fund's zone, with a numeric-offset token naming the zone when it is not WIB: `utc8` (Asia/Makassar) or `utc9` (Asia/Jayapura). A name with **no token is Asia/Jakarta, whenever it was written**, so every existing dump keeps its meaning and nothing a WIB instance writes changes shape. The parse reads the stamp in its own zone, so the instants stay exact: a zone change never re-dates an old file, the newest-first order never inverts, and the format-version check and retention keep working across it. The Cadangan card's date is the name's own date. Fresh downloads are named for the fund's day (`ZipFilename`, and the web names the file with the same `todayISODate`).
- **No email delivery** (cut by grill A, 2026-09-28). A backup carrying photos outgrows attachment limits, a JSON-only mail is the photo-less backup this ADR rejects, and a download link would be an unauthenticated copy of the whole fund. Emailed *reports* were considered and rejected too: members hold no email address (PRD section 6) and scheduled mail is the machinery reminders are built from (PRD section 4); the public report link, shared in the group chat, is that channel. `SMTP_URL` leaves [ADR-019](./019-cli-surface-and-runtime-config.md) with the code that removes it.

**Compatibility across versions** *(Grill A, 2026-09-28)*. `uruni.json` carries an integer **`format_version`**, separate from the app version and bumped only when the exported shape changes, so most upgrades leave old dumps restorable. Through `0.x` the importer accepts its own `format_version` and each older one it carries an upgrade step for (`ParseUpload` decodes the old shape and converts it, so the in-app restore, the inspect step and `uruni rebuild` only ever see the current one); it refuses a newer one and one older than its oldest step, and decodes with `DisallowUnknownFields` so nothing is silently dropped. Format 2 ([ADR-040](./040-effective-dated-tiers-and-rate-corrections.md)) adds a `member_tiers` array - every `member_tier` row, superseded ones included - and drops `members[].tier_id`; each `fund` entry gains `time_zone` ([ADR-041](./041-the-funds-time-zone.md): `Asia/Jakarta`, `Asia/Makassar` or `Asia/Jayapura`; `ParseUpload` refuses any other value, a missing field - the empty string - included, at inspect, and the schema's `CHECK` is the backstop at restore; the 1 to 2 step fills `Asia/Jakarta`, since every v1 file was written when the whole app reckoned in WIB, so restoring one onto an Eastern fund puts it back on WIB until she changes it again); each `dues_rates` entry gains `correction` (its number within the month; the highest stands) and `deleted` (a deleting correction, which copies the amount it withdrew), and the array carries every row, superseded and deleting ones included, because the trail is the data. The 1 to 2 step writes one row per tiered member from the month of `joined_on` and reads a v1 rate as `correction` 0, `deleted` false. Three things keep that safe: `serve` writes a fresh dump at boot when the newest dump's `format_version` differs from its own, so a restorable backup in the current format always exists; older-format backups stay downloadable and are listed as made by an older version, with a restore button when the importer can upgrade them and none when it cannot; and a checked-in golden `uruni.json` must round-trip exactly, so any schema edit that changes the export breaks a test and forces a conscious decision. Restoring onto an older binary is refused - rolling the image back is the operator's job.

**The `0.x` format rule** *(#516)*. `uruni rebuild` crosses a schema change on a backup the *old* binary wrote, so that backup has to stay readable: **a schema PR keeps the previous release's backup restorable as it is, or ships the step that converts its `format_version` in the same PR** (a `FormatVersion` bump without that step is a PR that strands every instance's last backup). The golden test alone does not prove it, since the golden is regenerated with the schema; `TestRebuildTakesThePreviousReleasesBackup` does: it takes the golden `uruni.json` as of the last tag (`cmd/uruni/testdata/previous-release/uruni.json`) through `ParseUpload` and `rebuild` into the current schema and proves the totals. That fixture is refreshed from the new tag whenever `URUNI_TAG` is bumped. The same rule is what the `v1.0.0` upgrade chain makes permanent.

**A raw snapshot before every upgrade** *(#517)*. A backup zip cannot be restored onto an older binary and `migrate down` is no rollback ([ADR-025](./025-one-migration-file-until-1.0.md): one step is the whole schema), so the way back from a bad upgrade is a copy of the database file the *old* binary opens. Every path that migrates (`serve`, `migrate up`, and `create-user` when a migration is pending) - and `uruni rebuild`, which replaces the file instead - takes the same guard first, under the instance lock and after the integrity check: when the running version is not the one recorded in `URUNI_BACKUP_DIR/uruni-boot-version`, it writes `VACUUM INTO` a copy there, `uruni-pre-upgrade-<date>-<time>_from-<version>_to-<version>.sqlite` (Asia/Jakarta, whatever the fund's zone is: the guard runs before migrations, on a database whose schema may predate `fund.time_zone`, so no fund can be read, and neither this file nor the `uruni.db.pre-...` copy `rebuild` sets aside is a day of the fund's or is read back as one - they are the only file names that keep a fixed stamp, [ADR-041](./041-the-funds-time-zone.md); temp file, fsync, rename, directory fsync, like a dump). The newest **3** are kept, a third quota beside the dumps' two; the name pattern is its own, so `ListDumps` and `ApplyRetention` never see it and its retention deletes only names it matched, after the marker is written. A database that has a schema but no marker (an instance upgrading into the first release with this) is snapshotted from `unknown`; an empty one (a first run) needs none. The marker holds `booted`, the last version a `serve` boot got all the way through (migrations, schema check), and `snapshotted`, the version already handled. A boot that fails after the copy and is retried by Docker finds `snapshotted` equal to its own version and writes nothing; a fix release tried while `snapshotted` is set and nothing has booted since writes nothing either, since no entries can exist that the copy lacks, so the real pre-upgrade copy is never evicted or relabelled. `booted` advances, and `snapshotted` clears, only on a successful `serve` boot, so going back to the old version and retrying the upgrade later snapshots again. If the snapshot cannot be written, the command refuses rather than migrate with no way back; the previous `URUNI_TAG` still runs against the untouched file. A plain restart writes and logs nothing, and builds left at version `dev` never snapshot between each other. To roll back: stop; delete `uruni.db-wal` and `uruni.db-shm` if present; put the newest snapshot in place of the database; delete `uruni-boot-version` (no marker plus a populated database snapshots from `unknown`, which is safe, where a stale marker could make a later retry skip its copy); run the previous tag. Entries made since the snapshot are lost and must be re-entered.

**`uruni rebuild --from <backup.zip>`: schema-changing upgrades in one command** *(#516, maintainer + grill, 2026-10-14)*. Through `0.x` the schema is one file edited in place ([ADR-025](./025-one-migration-file-until-1.0.md)), so a release that changes it leaves the old database unreadable by the new binary's queries and `serve` refuses it. The way across used to be eight hand-run steps (download a backup, stop, copy the raw file aside with a helper container, start the new image on an empty database, register on the public URL - which reopens the first-registration window - create a throwaway fund, restore, verify). `rebuild` is those steps in the binary, run by the operator with `serve` stopped. The zip is a backup the **old** binary wrote, normally one downloaded in-app just before stopping. There is no `--from-live`: the new binary cannot read the old schema. Nothing is written until every read-only check has passed, in this order:
1. The instance lock; the command refuses while `serve` holds it.
2. `ParseUpload`, with the upload's own caps and the totals check; and the backup must hold **exactly one login** (zero would leave a populated instance open to first registration, [ADR-030](./030-multi-fund-scoping.md); two is not a shape the app produces).
3. Refuse when the live schema already matches: restoring in the app is the tool for that case, and it keeps the live login and writes a safety-net dump.
4. The file's owner must be the running uid (the swapped-in file would otherwise be unwritable by whoever serves it), and the name the old file will be kept under must be free.
5. The staleness and identity gate, against the old file, in raw SQL with quoted identifiers (the store's queries are written against the new schema): row counts equal **both ways** for every table the backup and the file share except `session`, `idempotency_key` and goose's table (a backup older than the file loses entries; one with more rows is another instance's or a reset file; a table the old file lacks, such as `member_tier` against a pre-format-2 file, is reported as not compared); each fund's `(id, report_slug)` and the login's `(email, password_hash)` equal to the backup's; and it **fails closed** - if `transaction`, `fund`, `user` or `member` cannot be read it refuses. It prints what was and was not compared; a rename or an edit that adds or removes no row is undetectable and is said to be. An **absent** database skips the gate, and so does a **damaged** one (a failed open or `quick_check`), loudly: the damaged file is not snapshotted (the copy would write the damage into the backup directory) but is still kept aside byte for byte.

Then the writes. For a healthy old file the #517 guard takes the snapshot and the marker (`rebuild` never calls `MarkBooted`: nothing has booted, and the marker's `snapshotted <version>` is what keeps the following `serve` from copying the file a second time). An absent, empty or damaged old file gets neither, so the first `serve` afterwards takes one extra, harmless snapshot of the rebuilt file, labelled from `unknown`. The checks before this point read the old file through a read-only handle; only damage SQLite itself reports (`SQLITE_CORRUPT`, `SQLITE_NOTADB`, a failed `quick_check`) skips the gate, and a busy, locked or out-of-space error refuses instead. Then a **scratch file in the database's own directory** (not `/tmp`, a tmpfs under `read_only`; not `/backups`, another volume, where the final rename would fail with `EXDEV`): migrate the embedded schema, run the restore core with its totals proof, `quick_check` and the schema check, write the finished file out with `VACUUM INTO` through the atomic write helper (so it is fsynced and has no `-wal` or `-shm`), and check that file again read-only, including the total its funds sum to. Then the swap: the old file is copied aside, atomically, to `uruni.db.pre-<to-version>-<date>-<time>` next to it (never overwritten; the run refuses if the name exists), a `-wal` still holding frames is kept beside it as `<aside>-wal`, the old `-wal`, `-shm` and `-journal` are removed and the directory fsynced (a stale one would be replayed into the new file), and **one** `rename(scratch, uruni.db)` follows, then the directory fsync. If only that last fsync fails, the new file is already live: the run reports it and keeps the receipts it extracted. `uruni.db` is never absent, and a failure before the rename leaves it as it was. The new file takes the old file's mode. Stale scratch is swept at the start and removed on every failure path.

The restore core is shared with the in-app restore through two named entry points, not a flag: `Restore` (safety-net dump, the live login untouched, sessions and idempotency keys cleared) and `RestoreForRebuild` (no dump, since nothing live is being replaced; the backup's one login inserted with its id). The totals proof is identical. Output goes to stdout, never the log, because it carries amounts ([ADR-022](./022-logging-slog.md)): the backup's newest date and fund names, what was compared, and the totals as "backup says / rebuilt says" beside the old file's raw ledger sum where it can be read. `serve` writes **no dump on clean shutdown**: considered for this, dropped, to be revisited after two real rebuilds. `rebuild` is a `0.x` tool: the `v1.0.0` upgrade chain (below) re-scopes or removes it. `make upgrade-rehearsal BACKUP=<zip> [DB=<old file>]` runs it on a copy in a temp directory, and `image.yml`'s boot job runs it under `--read-only --cap-drop ALL`.

**To roll back a rebuild:** stop the app; delete `uruni.db-wal` and `uruni.db-shm` if present; move the new `uruni.db` aside and rename `uruni.db.pre-<version>-<date>-<time>` to `uruni.db`, and its `-wal`, if one was kept, to `uruni.db-wal` (the pre-upgrade snapshot in the backup directory is the same file's equal); delete `uruni-boot-version`; run the previous tag. Entries made since the rebuild are lost and must be re-entered. The `.pre-` file is never pruned; delete it once the upgrade has proven itself.

**A restore proves its numbers** *(Grill A, 2026-09-28)*. The export writes a `totals` block - derived balance per fund, per location and per purpose, integers, from the same balance queries the home screen's `ledger` functions wrap, read in the **one read transaction** that reads the rows, so a write can't land between them ([#496](https://github.com/kerti/uruni/issues/496)). Before any file is written - download, boot, daily or pre-restore dump - and again at the restore's inspect step, before the password prompt, the totals are re-summed from the document's own rows and a disagreement is refused. The import recomputes those from the rows it just inserted, inside the transaction, before `COMMIT`, and rolls back on any mismatch. A file hash would catch corruption but not an exporter bug writing consistent-but-wrong rows; totals in the ledger's own terms catch both. The confirm step's total is read from this block, so the number the treasurer confirms is the number the commit proved. Reconciliation snapshots restore as frozen history and are not re-run.

**Restore scope is the whole instance, today** *(Grill A, 2026-09-28)*. `user` is not fund-scoped ([ADR-030](./030-multi-fund-scoping.md)), so a restore rolls back every fund to the file's date. The confirm step names the cost per fund - live transactions whose id is past the file's highest id, e.g. "12 transaksi setelah 26 Sep akan hilang". Per-fund restore was rejected: id collisions against obligation 2, a split totals check, and a picker, for a case n=1 has not shown. **Tenancy, not now:** the file stays *tenant-shaped* - everything in it hangs off the `user` and its funds, nothing instance-level (no config, no instance id) - so a future multi-tenant build can restore one tenant by either a database per tenant or an order-preserving id remap, without a new format.

**The per-fund confirm line, precisely** *(grill, 2026-09-30, #325)*. The paragraph above names the shape for a fund present on both sides; the confirm step's list covers all three cases a whole-instance replace can produce, one line each, read straight off a comparison between the file and the live database - never computed twice, and never shown until the upload has already passed every check above:
- **Kept** (in both): if nothing of the live fund's history sits past the file's own cutoff for it, the line says so plainly (nothing would be lost); otherwise it names the count, e.g. "12 transaksi setelah 26 Sep akan hilang" - the sentence the paragraph above already promised.
- **Removed** (live only): named outright as gone, not folded into a silent "everything else stays" - restoring a whole instance means a fund the file never held is a fund the restored instance will not have either.
- **Added** (file only): named as what it is - a fund this instance does not have yet, arriving with the restore.

**Login is not restored, in the app** *(maintainer + grill, 2026-09-30, #325)*. The live `user` row is left completely untouched by the in-app restore (`uruni rebuild` is the exception and carries the backup's one login over: the file it builds has no live password to preserve, a populated instance with no login would be open to first registration - [ADR-030](./030-multi-fund-scoping.md) - and the lockout reasoning below rests on a treasurer with no server access, where the person running `rebuild` is the operator, who has it and can run `create-user`). In the app, the backup's own `users` are decoded (still under `DisallowUnknownFields` - a malformed `user` entry still refuses the whole file) and then simply never written anywhere. No table's foreign key points at `user` ([ADR-030](./030-multi-fund-scoping.md) decision 2 - it is the one table nothing else is scoped through), so there is nothing downstream that restoring it would even unblock. The confirm step's password re-entry checks the **current, live** password, not the file's - a password decoded from an old backup and then silently made live again is exactly how a treasurer locks herself out with a credential she no longer remembers typing. The only account reset this app has is `uruni create-user` on the host, which needs server access PRD section 7.10 rules out by design; restoring a stale password hash would trade a data problem for an access problem the app has no way to undo. Every session and every idempotency key is still cleared on a successful restore (unrelated to this ruling - a whole-instance data replacement warrants a fresh login regardless of whose password is live), and the treasurer signs back in with the password she just re-entered to confirm.

**The upgrade chain is a `v1.0.0` release gate, not a post-1.0 nicety.** The first step exists since `format_version` 2 (`internal/backup/upgrade.go`, v1 to v2, [ADR-040](./040-effective-dated-tiers-and-rate-corrections.md)); the gate is the chain being complete and kept. Once production data exists, a backup must restore on every later version, so the importer has to carry explicit per-version upgrade steps (`format_version` N to N+1). The production release must already ship with it; `v1.0.0` is not cut without it ([ROADMAP](../ROADMAP.md)). `uruni rebuild` is the `0.x` tool for the same job and goes when the chain lands, or is re-scoped by the ADR that adds it.

**Consequences.** The JSON schema needs its `format_version` field and a documented shape (own sub-doc when building).

**Two obligations the M2 schema puts on the import** (added 2026-08-12, from [ADR-024](./024-schema-conventions.md)):

1. **Insert in dependency order, or set `PRAGMA defer_foreign_keys=ON` inside the import transaction.** Fund scoping is enforced by composite foreign keys, so a child inserted before its parent is rejected rather than tolerated. **Within `"transaction"`, deferral is not enough** ([ADR-034](./034-envelope-participation.md), 2026-09-30): its `BEFORE INSERT` trigger reads the purpose a named contribution is tagged to and the row a reversal reverses, and triggers are never deferred. So purposes and members go in first, and every row with `reverses_transaction_id` set after the row it names - by dependency, not by id, since id order is not something new code may rely on. The triggers stay **on** during a restore: they are what refuses a hand-edited or corrupted backup.
2. **Preserve original integer ids verbatim** — never let SQLite reassign them. Ids are semantically load-bearing, not surrogate: `reconciliation.through_transaction_id` is a ledger cutoff whose meaning is id ordering, and every cross-table reference in a restored database has to keep pointing at the same row.

Both are cheap to honour when the importer is written and expensive to discover afterwards, which is why they are recorded here rather than at M8.

**The import half is load-bearing.** Since [ADR-004](./004-database-sqlite-only.md) makes SQLite the only engine through `0.x`, this document is also the **sanctioned engine-migration path**, not just disaster recovery. A round-trip test — export → fresh empty database → import → identical balances — is therefore required, not a nice-to-have.
