# ADR-012 — Backup & export implementation

**Status:** Accepted · `draft` — no code implements this yet, so it may still be edited in place · [ADR index](./README.md)

**Decision.**
- **JSON export**: Go `encoding/json` serializes all tables into one **versioned** document; a matching **import** restores it.
- **The backup is one `.zip`** (stdlib `archive/zip`): `uruni.json` plus a `receipts/` folder holding every receipt image under its stored, server-generated name. Import restores both. The JSON's own `version` is the only version; the zip adds no manifest. This keeps [ADR-011](./011-receipt-photos-local-volume.md)'s "the export references photo files rather than embedding them": the JSON names each file, the file sits beside it. A JSON-only download would restore `receipt` rows pointing at images that no longer exist; base64 inside the JSON was rejected (a third larger, and one parse holds every photo in memory). *(Grill A, 2026-09-28.)*
- **Restore is in-app and atomic** (Pengaturan, beside the download). It never swaps the database file: it replaces every row inside **one write transaction** on the already-open connection, so a bad file rolls back and a file swap's orphaned inode ([#278](https://github.com/kerti/uruni/issues/278)) cannot happen. The single connection (`SetMaxOpenConns(1)`, [ADR-004](./004-database-sqlite-only.md)) makes other requests wait for the commit, which is all a maintenance mode would have bought. Order: write a **safety-net backup** of the current state to the backup directory; extract receipt images into the uploads volume (additive; a name clash is the same file); then the row transaction. A failed commit leaves only orphan images, which ADR-011 already tolerates. The confirm step shows what the file holds (export date, funds, total) and asks for the password again - the treasurer's **current** password, not anything decoded out of the file; see "Login is not restored" below. Sessions are never exported, so a restore logs everyone out. The upload gets its own caps (body, unzipped total, entry count), refuses a backup newer than the running binary, and every image passes the receipt decode checks. A CLI `uruni import` is deferred until an engine migration needs it; the logic lives in one package so that stays cheap. *(Grill A, 2026-09-28.)*
- **Restoring one of the server's own stored dumps reuses this exact path** ([#326](https://github.com/kerti/uruni/issues/326)). The Cadangan card's list already addresses each dump by a server-side filename (`GET /api/backups/{name}`, validated the same way a download is); restore adds a second inspect route over that same identifier, `POST /api/restore/inspect-stored/{name}`, which reads the named file out of the backup directory, decodes it through the very same `backup.ParseUpload`, and hands the result to the same preview-then-stage tail an uploaded file goes through - so an old-format dump is refused by the same format-version check an old-format upload would hit, not a second, separately-maintained one. `POST /api/restore/confirm` is unchanged: it takes a token and a password and does not know or care which inspect route staged what it is confirming. Only a current-format dump is offered "pulihkan" in the UI - the list's existing `is_current_format` flag is exactly that signal, reused rather than duplicated. A safety-net dump from a previous restore is itself always current-format (it is built from the live `Document`, which is always exported in the running binary's own format), so it is restorable too - a restore can undo a restore.
- **The backup holds every table except `session`** - `user` included, so the zip carries a password hash and every name; the download copy says to keep it somewhere safe. The report slug lives on `fund`, so a restore keeps the link the group already has. *(Grill A, 2026-09-28.)*
- **Excel**: generated server-side with **excelize** - human-readable, not the restore path. **M8, not M6.** `.xlsx`, not CSV: Indonesian-locale Excel splits lists on `;`, so a comma CSV opens with every field crammed into column A. **Mirror, don't compute**: each sheet shows only what a screen already derives - Ringkasan (balances per location and purpose, latest reconciliation), Transaksi (receipt present as yes/no), Anggota, Amplop, Talangan, Rekonsiliasi - each with a Dana column rather than a sheet per fund. Amounts are number cells with a rupiah number format, never text. Raw tier/rate tables, a separate transfer sheet and the images are left out. A member-by-month dues grid goes in only if the app already derives one by M8. *(Grill A, 2026-09-28.)*
- **Scheduled dumps**: once a day, in-process ([ADR-013](./013-scheduling-in-process.md)), `serve` writes the same backup zip to `URUNI_BACKUP_DIR` (default `./backups`, `/data/backups` in the container; boot-checked like `URUNI_UPLOADS_DIR`) - **only if the fund changed** since the last dump, judged by a hash of `uruni.json` plus the receipt file list. So retention counts *versions*, not days: the last **7** daily dumps are kept, plus the last **3** safety-net backups from restore, in separate quotas. On by default with no switch - retention is bounded, so there is nothing to turn off for. The Pengaturan backup card lists them (date, kind) with download and restore; restoring from one runs the same atomic path as an upload, minus the upload. Dumps on the same disk do not survive losing the disk: off-site copies (e.g. syncing `URUNI_BACKUP_DIR` to object storage with rclone or restic) are a **self-host README recommendation**, never an app feature - what the operator does with their machine is outside the app. No download reminder in the app (PRD section 4: no reminders). *(Grill A, 2026-09-28.)*
- **No email delivery** (cut by grill A, 2026-09-28). A backup carrying photos outgrows attachment limits, a JSON-only mail is the photo-less backup this ADR rejects, and a download link would be an unauthenticated copy of the whole fund. Emailed *reports* were considered and rejected too: members hold no email address (PRD section 6) and scheduled mail is the machinery reminders are built from (PRD section 4); the public report link, shared in the group chat, is that channel. `SMTP_URL` leaves [ADR-019](./019-cli-surface-and-runtime-config.md) with the code that removes it.

**Compatibility across versions** *(Grill A, 2026-09-28)*. `uruni.json` carries an integer **`format_version`**, separate from the app version and bumped only when the exported shape changes, so most upgrades leave old dumps restorable. Through `0.x` the importer accepts **only its own** `format_version`; it refuses a newer one, and decodes with `DisallowUnknownFields` so nothing is silently dropped. Three things keep that safe: `serve` writes a fresh dump at boot when the newest dump's `format_version` differs from its own, so a restorable backup in the current format always exists; older-format backups stay downloadable but are listed as made by an older version, with no restore button; and a checked-in golden `uruni.json` must round-trip exactly, so any schema edit that changes the export breaks a test and forces a conscious bump. Restoring onto an older binary is refused - rolling the image back is the operator's job.

**A restore proves its numbers** *(Grill A, 2026-09-28)*. The export writes a `totals` block - derived balance per fund, per location and per purpose, integers, from the same `ledger` functions the home screen uses. The import recomputes those from the rows it just inserted, inside the transaction, before `COMMIT`, and rolls back on any mismatch. A file hash would catch corruption but not an exporter bug writing consistent-but-wrong rows; totals in the ledger's own terms catch both. The confirm step's total is read from this block, so the number the treasurer confirms is the number the commit proved. Reconciliation snapshots restore as frozen history and are not re-run.

**Restore scope is the whole instance, today** *(Grill A, 2026-09-28)*. `user` is not fund-scoped ([ADR-030](./030-multi-fund-scoping.md)), so a restore rolls back every fund to the file's date. The confirm step names the cost per fund - live transactions whose id is past the file's highest id, e.g. "12 transaksi setelah 26 Sep akan hilang". Per-fund restore was rejected: id collisions against obligation 2, a split totals check, and a picker, for a case n=1 has not shown. **Tenancy, not now:** the file stays *tenant-shaped* - everything in it hangs off the `user` and its funds, nothing instance-level (no config, no instance id) - so a future multi-tenant build can restore one tenant by either a database per tenant or an order-preserving id remap, without a new format.

**The per-fund confirm line, precisely** *(grill, 2026-09-30, #325)*. The paragraph above names the shape for a fund present on both sides; the confirm step's list covers all three cases a whole-instance replace can produce, one line each, read straight off a comparison between the file and the live database - never computed twice, and never shown until the upload has already passed every check above:
- **Kept** (in both): if nothing of the live fund's history sits past the file's own cutoff for it, the line says so plainly (nothing would be lost); otherwise it names the count, e.g. "12 transaksi setelah 26 Sep akan hilang" - the sentence the paragraph above already promised.
- **Removed** (live only): named outright as gone, not folded into a silent "everything else stays" - restoring a whole instance means a fund the file never held is a fund the restored instance will not have either.
- **Added** (file only): named as what it is - a fund this instance does not have yet, arriving with the restore.

**Login is not restored** *(maintainer + grill, 2026-09-30, #325)*. The live `user` row is left completely untouched by a restore: the backup's own `users` are decoded (still under `DisallowUnknownFields` - a malformed `user` entry still refuses the whole file) and then simply never written anywhere. No table's foreign key points at `user` ([ADR-030](./030-multi-fund-scoping.md) decision 2 - it is the one table nothing else is scoped through), so there is nothing downstream that restoring it would even unblock. The confirm step's password re-entry checks the **current, live** password, not the file's - a password decoded from an old backup and then silently made live again is exactly how a treasurer locks herself out with a credential she no longer remembers typing. The only account reset this app has is `uruni create-user` on the host, which needs server access PRD section 7.10 rules out by design; restoring a stale password hash would trade a data problem for an access problem the app has no way to undo. Every session is still cleared on a successful restore (unrelated to this ruling - a whole-instance data replacement warrants a fresh login regardless of whose password is live), and the treasurer signs back in with the password she just re-entered to confirm.

**The upgrade chain is a `v1.0.0` release gate, not a post-1.0 nicety.** Once production data exists, a backup must restore on every later version, so the importer has to carry explicit per-version upgrade steps (`format_version` N to N+1). The production release must already ship with it; `v1.0.0` is not cut without it ([ROADMAP](../ROADMAP.md)).

**Consequences.** The JSON schema needs its `format_version` field and a documented shape (own sub-doc when building).

**Two obligations the M2 schema puts on the import** (added 2026-08-12, from [ADR-024](./024-schema-conventions.md)):

1. **Insert in dependency order, or set `PRAGMA defer_foreign_keys=ON` inside the import transaction.** Fund scoping is enforced by composite foreign keys, so a child inserted before its parent is rejected rather than tolerated. **Within `"transaction"`, deferral is not enough** ([ADR-034](./034-envelope-participation.md), 2026-09-30): its `BEFORE INSERT` trigger reads the purpose a named contribution is tagged to and the row a reversal reverses, and triggers are never deferred. So purposes and members go in first, and every row with `reverses_transaction_id` set after the row it names - by dependency, not by id, since id order is not something new code may rely on. The triggers stay **on** during a restore: they are what refuses a hand-edited or corrupted backup.
2. **Preserve original integer ids verbatim** — never let SQLite reassign them. Ids are semantically load-bearing, not surrogate: `reconciliation.through_transaction_id` is a ledger cutoff whose meaning is id ordering, and every cross-table reference in a restored database has to keep pointing at the same row.

Both are cheap to honour when the importer is written and expensive to discover afterwards, which is why they are recorded here rather than at M8.

**The import half is load-bearing.** Since [ADR-004](./004-database-sqlite-only.md) makes SQLite the only engine through `0.x`, this document is also the **sanctioned engine-migration path**, not just disaster recovery. A round-trip test — export → fresh empty database → import → identical balances — is therefore required, not a nice-to-have.
