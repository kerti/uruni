# ADR-028 — Testing the trust core: `internal/money` and `internal/ledger`

**Status:** Accepted · `draft` — no code implements this yet, so it may still be edited in place · [ADR index](./README.md)

**Context.** [ADR-015](./015-testing-money-math.md) (itself `draft`) already names `go test` and "the ledger/reconciliation logic as the highest-priority target," without saying how a test gets a real SQLite to run against. M2 already answered a version of that question for its own package: `internal/db`'s tests open a real temp file, deliberately not `:memory:`, because — per that package's own comment — "the pragmas under test (WAL especially) behave differently for an in-memory database, which would make the test prove less than it appears to." M3's premise, set by the maintainer, calls for `:memory:` instead. This ADR reconciles the two rather than picking one blind.

## Decision

**Harness: reuse `internal/db.Open(ctx, ":memory:")` + `internal/db.Up(ctx, sqlDB, logger)`. No second connection-opening helper.**

Verified empirically (see the M3 plan) rather than assumed:

- `internal/db.Open`'s DSN already carries `foreign_keys(ON)` as a query parameter the driver replays on **every** connection it opens — file or `:memory:` alike. The well-known "foreign keys default off, per connection" gotcha is closed by reusing plumbing that already exists, not by a pragma call written specifically for tests.
- `journal_mode(WAL)` silently falls back to SQLite's own "memory" journal mode on an in-memory database (`PRAGMA journal_mode=WAL` against `:memory:` reports back `memory`, confirmed with the `sqlite3` CLI). This is harmless for what `internal/ledger`'s tests check — `CHECK`s, composite FKs, triggers, derived sums — and is exactly why `internal/db` keeps its *own* tests on a real file: those tests assert the WAL pragma itself, which `internal/ledger`'s tests never do.

So the harness is not new code so much as a new *call*: `db.Open(ctx, ":memory:")` returns a `*sql.DB` configured identically to production (`SetMaxOpenConns(1)`, all four pragmas replayed, `foreign_keys=ON`), and `db.Up` applies the one migration file on top of it.

**Per-test isolation: no `cache=shared`, no shared DSN.** Each test opens its own private `:memory:` database via a fresh `db.Open` call. This is safe *specifically because* [ADR-004](./004-database-sqlite-only.md) forces `SetMaxOpenConns(1)`: a private (non-shared-cache) `:memory:` database only becomes a problem across multiple connections, each seeing its own empty database, and this pool never opens a second one. **Note for whoever later revisits connection pooling:** raising `MaxOpenConns` above 1 would silently break this harness — a second connection would see an empty database with none of the first connection's rows — so a superseding ADR for pooling should re-read this one too, not just [ADR-004](./004-database-sqlite-only.md).

**A small local helper, not a shared exported one.** `internal/ledger`'s own test files get a `newTestLedger(t) *Ledger` (or equivalent), mirroring `internal/db`'s `migratedTestDB(t) *sql.DB`: wraps `Open` + `Up` + `t.Cleanup(Close)`. Fixtures are a small builder type local to the package (one fund with its accounts/purposes/members, built through the same `store.CreateX` calls `internal/db`'s `ledgerFixture`/`scenarioFund` already use) rather than raw inserts scattered through every test. It is not the *same* helper as `internal/db`'s — those are unexported and live in a different package — but the same shape, deliberately: one more small fixture file is cheaper than exporting test-only surface across a package boundary for it.

**Money arithmetic: table-driven tests. No property-based testing, no `testing/quick`.** `internal/money` has three checked operations and a conversion pair. The interesting input space — `0`, `1`, `-1`, `math.MaxInt64`, `math.MinInt64`, one past overflow in each direction — is short and enumerable by hand. `Sub` with `math.MinInt64` as the **subtrahend** is a required case, not an optional one: an implementation written as `Add(-b)` wraps around there and returns a confidently wrong number. No live call site can reach it today — `recorded_amount` is `SUM`-bounded — but `actual_amount` is a figure the treasurer types, so the one unbounded input in the trust core meets the one asymmetric operation in it. A generator's advantage (exploring a space a human can't) doesn't apply at this size. `testing/quick` has no shrinking and is barely maintained even as stdlib packages go; reaching for it, or a third-party property-testing library, for three functions is machinery bought for a problem this size doesn't have, against `CLAUDE.md`'s stdlib-first tiebreak.

**Ledger and reconciliation: table-driven scenario tests, in the shape `internal/db` already established — not golden files.** `TestReconciliationRecordsWhatWasCountedAndHowItWasResolved` (in `internal/db/scenario_test.go`) is the reference: build a fund, post entries, assert derived figures directly. Golden-file diffing earns its keep against large structured output (rendered HTML, a JSON export); a reconciliation snapshot is a handful of `int64` and `string` fields, better asserted with a direct `if got != want` than serialized and diffed against a fixture file nobody reads.

**Coverage bar: `internal/money` ≥ 90%, `internal/ledger` ≥ 85%.** Reviewed at the PR that lands each slice — `CLAUDE.md`'s "review this hardest" instruction for M3 is the enforcement mechanism, not new CI machinery. `codecov.yml`'s existing project-wide `target: auto, threshold: 1%` already catches a regression a low-coverage addition here would cause, at the whole-project level. A **hard per-package minimum** would need a new `component_management` block in `codecov.yml`, and is **declined** (2026-08-12): it is CI machinery bought before any drift has happened, against a bar no slice has missed yet, and `CLAUDE.md`'s "fewest moving parts" tiebreak applies to the build as much as to the binary. Revisit if a slice ever lands under the bar and the review does not catch it — that is the evidence this would need.

**What [ADR-015](./015-testing-money-math.md) should say — named here, not edited here.** ADR-015 stays the test-*pyramid* policy (`go test`/Vitest/Playwright, priority order); this ADR is the mechanics underneath its highest-priority line. The concrete edit, for whoever implements this slice and drops ADR-015's `draft` tag: append one sentence to its Consequences, e.g. *"`internal/money` and `internal/ledger` carry a numeric coverage bar (≥90% / ≥85%), reviewed per slice; harness and fixture mechanics are [ADR-028](./028-testing-the-trust-core.md)."*

## Consequences

`internal/ledger`'s test files import `internal/db` (for `Open`/`Up`) and `internal/store` — both already export what's needed, so this costs no new exported surface anywhere.

A test failure here always means either an arithmetic mistake or a schema/domain disagreement, never a mock disagreeing with reality: no `Querier` fake stands between a ledger *write* test and the real `CHECK`s, composite FKs, and immutability triggers M2 built.
