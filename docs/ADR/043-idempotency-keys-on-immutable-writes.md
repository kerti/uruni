# ADR-043 - Idempotency keys on immutable writes

**Status:** Accepted · implemented in the Production milestone (epic [#523](https://github.com/kerti/uruni/issues/523): [#634](https://github.com/kerti/uruni/issues/634) the table, the fetch wrapper and `POST /api/transactions`, [#635](https://github.com/kerti/uruni/issues/635) the other seven routes) - drafted 2026-10-20 ([#633](https://github.com/kerti/uruni/issues/633)), grilled and approved by the maintainer 2026-10-20 · supersedes nothing · reads [ADR-004](./004-database-sqlite-only.md), [ADR-008](./008-pwa-no-offline-data.md), [ADR-012](./012-backup-and-export.md) (one sentence gains a table, edited in #634's PR with the code), [ADR-013](./013-scheduling-in-process.md), [ADR-024](./024-schema-conventions.md) and [ADR-027](./027-ledger-domain-boundary.md) · [ADR index](./README.md)

**Context.** A treasurer on a phone taps *Simpan* and the connection drops. Either the request never arrived or its response never came back, and the browser cannot tell which. [#507](https://github.com/kerti/uruni/issues/507) made the app say so: a write waits a bounded 20 seconds (two minutes for an upload), a thrown fetch becomes `write_outcome_unknown`, the screen re-reads its data, and the copy asks her to check Riwayat before saving again. It kept [ADR-008](./008-pwa-no-offline-data.md) whole: nothing is queued, offline stays unavailable. What it could not do is make the retry safe. Transactions are immutable (CLAUDE.md rule 3), so a retry of a write that had in fact committed is a second row that only a reversal or a correction removes. That is TC-3 of the 2026-10-12 technical assessment, whose real fix #507 left to this epic.

Some routes are already safe to repeat, each for its own reason: settling a claim (`reimbursement_settled_once`), a reversal (`dues_payment_reversed_once`, and ADR-042's once-only index), closing and reopening an envelope (`ErrIncidentalAlreadyClosed`, `ErrIncidentalNotClosed`), setup and register (`ErrFundAlreadyExists`, `ErrAlreadyRegistered`). A duplicate from a config route is visible beside the form it was made on, and can be deleted, with two exceptions found below: a pass-through purpose, which moves no money and stays unkeyed (finding 2), and a location opened with a starting balance, which does move money and is keyed (finding 4). Eight routes are neither safe to repeat nor reliably deletable, and a repeat of each is checked against the code below:

| Route | Ledger method | Answers | A repeat today |
|---|---|---|---|
| `POST /api/transactions` | `PostTransaction` | 201 | a second row |
| `POST /api/dues-payments` | `PostDuesPayments` | 201 | a second row per period (a period already paid is not refused; payments accumulate) |
| `POST /api/transfers` | `PostTransferBetweenAccounts` | 201 | a second pair |
| `POST /api/purpose-moves` | `PostPurposeMove` | 201 | a second pair, unless the source purpose can no longer cover it |
| `POST /api/transactions/{id}/purpose-correction` | `PostPurposeCorrection` | **200** | refused if it repeats the last correction, otherwise a second pair (verified below) |
| `POST /api/incidentals` | `OpenIncidental` | 201 | a second purpose and envelope |
| `POST /api/reconciliations` | `TakeReconciliation` | 201 | a second snapshot, and for `entry_added` a second fix row (verified below) |
| `POST /api/accounts` | `CreateAccount` | 201 | a second location, and with a starting balance a second `opening` row that cannot be deleted (verified below) |

Drafted from #633 and read against #634, #635, #507 and ADRs 040-042, before any of its code existed.

## Decided before the grill

Recorded as decided (maintainer, 2026-10-19); not reopened here.

- **The client sends a key on every mutating request**, from the one fetch wrapper: uniform, nothing per form.
- **The server honours a key only on the immutable routes listed above.** The other writes ignore the header. (The list was seven on 2026-10-19; `POST /api/accounts` joined it at approval, below.)
- **Once-only routes keep their 409** (settle, reversals, close, reopen, setup, register). Where the client knows a request is a retry after an unknown outcome, the UI may treat "already done" as success, as ADR-042 already says of a reversal.
- **Config and deletable routes get no server key**: members, tiers, rates, pass-through purposes, reimbursement claims, receipts, and the rest of the location routes (rename, retire, delete). The list put pass-through purposes and the creation of a location under "deletable", and neither is: a pass-through purpose stays unkeyed as an accepted risk (finding 2), and creating a location was keyed at approval (finding 4).
- *Leans for the grill, settled below:* a table outside the backup, like `session`; 24 hours' retention, purged lazily (in the write's own transaction, not [#608](https://github.com/kerti/uruni/issues/608)'s hourly sweep for sessions, see Retention); a reused key with another body answers 409.

## Decision

**A write that carries an `Idempotency-Key` on one of the eight keyed routes is recorded, with the result the ledger returned for it, in the same database transaction as the rows it posts. The same key with the same request, within 24 hours, is answered with that recorded result, mapped as a first success is, and posts nothing.** A key is a request's nonce, not a queue entry and not a row id: nothing is stored durably on the device, nothing retries by itself, and [ADR-024](./024-schema-conventions.md)'s "nothing generates ids client-side" stays true.

**On the wire.**
- *Header.* `Idempotency-Key`, minted by the client: 16 random bytes from `crypto.getRandomValues`, written as 32 hex characters. (Not `crypto.randomUUID`, which throws on a non-secure origin such as a phone testing against a LAN address.) The server asks only for 16 to 64 characters of `[A-Za-z0-9_-]`. A malformed key on a keyed route is 400 `invalid_idempotency_key`; **an absent key is not an error**, the write is simply unprotected, so curl, e2e API seeding and a PWA bundle cached from before this release keep working. On any other route the header is not read at all.
- *Which requests.* A route is keyed or it is not; the body never decides. `POST /api/accounts` is keyed for every create, with a starting balance or without. The money risk is the create with a balance (an immutable `opening` row that cannot be deleted, finding 4), but a rule that keyed only that case would make the server's behaviour depend on the body, and a replay of a create without a balance is harmless: it returns the location already made and spares an empty duplicate that would need deleting. The other routes under `/api/accounts` (rename, retire, delete) stay unkeyed.
- *Fingerprint.* The SHA-256 of the method, the request path (so the id in `/api/transactions/{id}/purpose-correction` counts; the route pattern would not) and the canonical body: the JSON decoded with `UseNumber` and encoded again, which sorts keys and drops whitespace but keeps each number's own text. A body that is not JSON hashes as its raw bytes; its handler answers 400 and nothing is recorded. Canonical rather than raw so that a retry from any client that orders keys differently is still the same request; a number written another way is a different request, which errs towards a 409, never towards a silent replay. (One hand-written shape escapes that: a body that repeats a key in two letter cases, `amount` and `Amount`, canonicalises alike whichever comes last, while Go's decoder honours the later one; spiked. The SPA writes each field once.) The wire body is hashed, not the decoded request struct, so that a deploy which changes a struct cannot change the fingerprint of a retry still waiting to be made.
- *Replay.* The recorded result, handed back where a fresh one would be. The handler maps it exactly as it maps a first success, so the route's own status (200 for the purpose correction, 201 for the rest) and wire shape come with it, and adds `Idempotent-Replayed: true`. The replay sits behind the session gate like the write it repeats.
- *Reuse.* The key found with another fingerprint is 409 `idempotency_key_reused`.
- *Only a commit records.* A refusal (400, 404, 409, 500) writes no key, so the retry of a write that failed is judged afresh against the state of the day. There is no "in progress" state and no third response for a concurrent twin: the single connection ([ADR-004](./004-database-sqlite-only.md)) runs transactions one at a time, and the second request finds the first's key already committed (spiked: 20 concurrent requests on one key posted one row and replayed 19 times, also under `-race`). That rests on the single connection: if the writer/reader split ADR-004 names as its upgrade path ever lands, the check must run in a write-locking (`BEGIN IMMEDIATE`) transaction, or two twins could both read "absent".

**The record.** One table, outside the backup, request-scoped state like `session` (a sketch of the shape; #634 owns the migration text, and the `CHECK`s and the column named `key` were run through SQLite and sqlc v1.31.1 on a scratch copy, the table as it now stands through SQLite again):

```sql
CREATE TABLE idempotency_key (
  key         TEXT    PRIMARY KEY CHECK (length(key) BETWEEN 16 AND 64 AND key NOT GLOB '*[^A-Za-z0-9_-]*'),
  fingerprint TEXT    NOT NULL CHECK (length(fingerprint) = 64),
  result      BLOB    NOT NULL,            -- what the ledger method returned, as JSON; not the HTTP reply
  created_at  INTEGER NOT NULL,            -- UTC unix seconds (ADR-024)
  expires_at  INTEGER NOT NULL CHECK (expires_at > created_at)
) STRICT;
CREATE INDEX idempotency_key_by_expiry ON idempotency_key(expires_at);
```

No `fund_id` (as `session` has none: a key proves a request by the treasurer, [ADR-030](./030-multi-fund-scoping.md)), no foreign key, no immutability trigger (a row is written once and deleted whole, and it is plumbing, not a record of the fund). Every time in it is an instant; no business date or period is involved, so [ADR-041](./041-the-funds-time-zone.md) has nothing to say here. A table rather than a cache in memory, because the moment a key matters most is a flaky network, and a restart or a deploy must not forget it; and rather than a column on `transaction`, which would reach one of the several tables these routes write, would sit in the backup for ever, and could not name a write that posts three rows or none.

**Where the check lives under ADR-027: in the ledger, inside the write's own `withTx`.** The ledger owns its transaction and the only connection, so a transaction opened around the ledger's call (by a handler, or by a middleware) would make the ledger's own `BeginTx` wait for a connection the wrapper holds: the hang ADR-027 verified. A handler could not even share it: every handler reads the fund through the pool (`resolveFund`) before it reaches the ledger, and the session gate reads the login the same way. The key therefore rides in. Each of the eight params structs gains an optional `Idempotency` value (the key, the fingerprint, the HTTP layer's `now` and `expires_at` in unix seconds, and a flag, with the record's age, that the ledger sets when the answer is a replay); nil means unkeyed, which is every existing caller, test, the CLI seed and restore. The eight methods share one small generic helper over `withTx`, working on the transaction's own `store.Querier` (the `...Tx` idiom of `postTransferPairTx`, never a second `withTx`):

1. *Check.* Read the key where `expires_at > now`. Found with the same fingerprint: decode the stored result into the method's own result type, set the replay flag and return it, writing nothing (the transaction ends empty and rolls back). Found with another: `ErrIdempotencyKeyReused`. Absent: delete every expired row, which also clears an expired row of this very key that nothing has removed yet (spiked: a plain insert over one trips the primary key), and go on.
2. *Write*, exactly as today.
3. *Record.* Marshal the method's result and insert the row. A primary-key collision here is impossible, because step 1 and this insert share one transaction on one connection; it would be a bug and answers 500 with nothing written. The insert is the one step after the write that can fail.
4. *Commit.* The rows and the key land together or not at all. A failed insert rolls the write back, and that is the crash-between test: #634 hands the insert a row the table's own `CHECK` refuses (an `expires_at` that is not after `created_at`) and asserts zero ledger rows and zero keys (spiked).

**What is stored is the ledger's result, not the HTTP reply.** The record holds the value the method returned, as JSON: `store.Transaction`; the dues payment's `[]store.Transaction`; `store.Transfer` for the transfer, the purpose move and the purpose correction; `store.Incidental`; `store.Reconciliation`; `store.Account`. The handler maps it to the wire exactly as it maps a fresh one, so a replay is a first success that the handler tells apart only by the flag. The alternative weighed was to build the reply inside the transaction with a function the handler hands in (a "seal") and to store its status and bytes; it is refused below, for four reasons. The ledger would call HTTP-shaped code from inside its transaction, where one read through the pool waits for the connection the transaction holds (spiked: it ran to the request's deadline), and the reconciliation's reply is exactly such a read. A status would be stored that the handler already owns. Stored bytes go stale across a release that edits a mapper, where a stored result is re-mapped by today's. And a replay would have to leave the ledger as something other than its return value (an error, or bytes in an out-parameter); here it is the return value, with only a flag beside it. The round trip is lossless: a `store` struct is integers, strings and pointers to them, and with `emit_json_tags: false` its keys are Go field names on both sides, never wire names (spiked: all eight types round-trip under `reflect.DeepEqual`, a maximal amount and a note with quotes, `<`, `&` and an accent included). A store struct changes only with the schema; through `0.x` a schema change is a rebuild that starts this table empty, so a stored result is never decoded into another shape, and after `v1.0.0` an added column reads as its zero value in a result at most 24 hours old (the decode ignores unknown fields and does not insist on known ones), which is harmless. The reconciliation needs nothing special. Its handler reads the snapshot's detail after the commit, as it does for a first success, and the snapshot and its lines are immutable, so a replay reads what the first answer did; if that read fails with a 500, the client counts any 5xx as unanswered (below), and the retry replays the snapshot and reads again.

Argument-shape validation stays before `withTx` ([ADR-027](./027-ledger-domain-boundary.md)), so a replay re-runs it. It is a function of the same body, the clock and, once [#632](https://github.com/kerti/uruni/issues/632) and [ADR-041](./041-the-funds-time-zone.md) land, the fund's zone, so a request that was good stays good unless the zone moves west inside the retry window (a narrowing of up to two hours around a day's turn); a ceiling checked inside the transaction, after step 1, is never met by a replay at all. The handler's part is small: a `keyed` middleware on exactly the eight routes reads the header, bounds and hashes the body (the same 1 MiB cap and 413 as `decodeJSON`) and puts it back; each handler passes the `Idempotency` value it builds from that and, after the call, adds `Idempotent-Replayed` when the ledger flagged a replay; the 409 reaches the client through the one error switch in `mapLedgerError`. Handlers still decode and map and add no check of their own. (The helper is generic over the result type; its exact shape is the builder's call.)

**Retention and the purge.** A row lives 24 hours from its commit. Long enough for a night without signal, a restart or a deploy; short enough that the table holds a day's writes, tens of small rows. Reads ignore an expired row, so correctness never waits on removal. Expired rows are purged **in the write that needs the room**: step 1's miss path deletes every row with `expires_at <= now` in the same transaction, before the write. There is no sweeper, no ticker, no timer and no state to keep. [ADR-013](./013-scheduling-in-process.md) permits an in-process ticker (the daily dump uses one); this table needs none. The hourly compare-and-swap of `sessionStore.maybeSweep` ([#608](https://github.com/kerti/uruni/issues/608)) exists because every authenticated request, a plain GET included, commits a session; a keyed write is already a write transaction, a handful a day, so a throttle would only add the state it exists to avoid. An idle instance keeps its last day of rows until the next keyed write, which is harmless. The time it reads is the handlers' injectable `now`.

**Restore, rebuild, backup.** The backup holds every table except `session` and `idempotency_key`: both are state of the running server, not of the fund. `Document`, `BuildDocument` and the rebuild gate (built from `Document`) never name it. **Restore clears it in the same transaction**, beside `DeleteAllSessions` in `restoreCore`, and not only for tidiness: a restore returns the ledger to an older state, and a key from the hour before would replay a success whose rows the restore has just removed (or whose ids now name other rows), so the retry that should post again would be told it had. `uruni rebuild` runs the same core over a file it built itself, so the table starts empty there by construction and the clear is a no-op. The boot schema guard (`db.CheckSchema`) compares the whole schema and refuses a file without the table with no new code.

**The client: one rule in the wrapper.** `apiFetch` adds the header to every non-GET, non-HEAD request (the methods it already treats as writes), merging with any headers the caller set. It keeps a module-level map from the request's identity (method, path and body text) to `{key, at}`, **in memory only**: nothing in `localStorage` or IndexedDB, so ADR-008 and rule 4 are untouched. The module exports a reset for tests, as ADR-041's zone does: module state outlives a Vitest case, and a key left by one test would be reused by the next.
- *Remembered from the send until a definite response.* The first send of a request mints a key and remembers it. An identical write issued while a key is remembered reuses it. That covers a retry after a lost response, and a second request sent before the first has an outcome at all (the lean in #633 names only the first). The second never comes from a tap: every keyed form disables its button while a write is in flight (`canSubmit` requires `!submitting` in Catat, and the dues and reconciliation forms do the same; the correction, envelope and location dialogs use `busy`), so it comes from a script, a test, or a caller that aborted and submitted again. It costs nothing, being the same identity map, but it is why #634's journey is a lost response followed by Simpan again, not a double tap (Consequences).
- *Definite is a 2xx or a 4xx*: an answer that proves the request was judged. The entry is dropped. **Everything else is indefinite** and leaves the entry in place with `at` set to now: a fetch that threw, a timeout, a caller's abort, and any 5xx. A 5xx without the API's error envelope (a proxy's 502 or 504: the app may have committed before Caddy gave up) is indefinite, and so is an enveloped 500, because the envelope proves the app answered, not that nothing committed. A handler can fail after its commit (`takeReconciliation` reads the snapshot back once the write is done), and a commit can fail after it reached the disk. A key kept across a 500 costs nothing, since a request the server refused records no key and the retry is judged afresh. An indefinite outcome touches only an entry that still holds its own key and never creates one, so a twin that times out after another twin's definite answer cannot bring a spent key back.
- *Forgotten 15 minutes after `at`.* A request identical to a forgotten one gets a fresh key. `at` moves with every failed attempt, so a key can outlive 15 minutes of real time while she keeps retrying; the server's 24 hours covers that chain and nothing else, since the client never reuses a key older than its last failure plus 15 minutes.
- *Two deliberate identical entries do not merge unless the first never got an answer*: a definite response drops its key before the second is sent, so the only way to reuse a key is to repeat a request that has had no answer yet (the accepted merge, below). A body that is not a string (a `FormData` upload) is never remembered and gets a fresh key each time; the server ignores it anyway.
- The map holds the body text, so a login body sits in memory after a lost response, until a definite answer or 15 minutes; the page already holds the same text in its form.

The existing `settleUncertainWrite` re-read after a lost response is unchanged. A reload forgets the keys, and with them the form (an installed PWA the phone evicted in the background comes back the same way): the retry of a save whose outcome was lost across a reload is a new request, the one case where checking first is still the advice. A second tab or device has a map of its own and is the same case. It has two more kin: a retry after the 15 minutes, and a retry whose body differs (a form that computes today's date at submit time, as Tambah lokasi does, sends another body after midnight, and another body is another key).

**What the treasurer sees on a replay: the same thing as the first success.** The screen takes the 201 it asked for and carries on. The wrapper can read `Idempotent-Replayed`, but nothing in the app shows it (settled below: no replay UI in v1), and the server logs one info line with the route and the age of the stored result, never the key or the body ([ADR-022](./022-logging-slog.md)). The age is what tells an operator at 22:00 a retry (seconds) from a swallowed deliberate entry (minutes); `idempotency_key_reused`, which the app cannot produce, is logged at warn. The two new codes, `invalid_idempotency_key` and `idempotency_key_reused`, are unreachable from the UI (the wrapper never sends a malformed or a reused key) and get entries in the shared error map with `invalid_json`'s existing wording, "Ada yang tidak beres saat mengirim data. Coba lagi."; the 409 is a definite response, so her next try carries a new key.

## What the verifications found

Run against the code, and the first, third and fourth on a scratch copy of HEAD (a throwaway test over `newTestLedger`, outside the repo). The first three are #633's questions; the fourth is the grill's.

1. **A duplicate purpose correction does not post a second pair when it repeats the last correction, and that is not enough.** `Ledger.PostPurposeCorrection` (`internal/ledger/purpose_correction.go`) reads the row's effective tag (`EffectivePurposeForTransaction`, `internal/store/queries/transfer.sql`) and returns `ErrPurposeCorrectionNoop` when the target equals it (`TestPostPurposeCorrectionRejectsNoop`). Two concurrent copies serialise on the one connection, so the second refuses too. Spiked: after A to B, the repeat was refused (2 transfer legs before and after). But the refusal compares against *now*, not against the request. After A to B and then B to A (4 legs), a late retry of the first A to B posted another pair (6 legs). And a refusal answers 409 `purpose_correction_noop` ("Baris ini sudah memakai pos itu.") to a treasurer whose save worked. The route stays in scope: the key turns both into the original 200.
2. **Envelopes are not deletable, so `/api/incidentals` stays keyed.** `internal/http/api.go` registers no DELETE for `/incidentals` or `/purposes`; no query in `internal/store/queries` deletes from `purpose` or `incidental` outside `restore.sql`'s clear-alls; the ledger deletes only a tier and a claim (`DeleteDuesTier`, `DeleteReimbursement`). `purpose` has no uniqueness on its name (only `purpose_single_main`), so a repeat of `OpenIncidental` writes a second purpose and incidental, and the duplicate can be renamed (`PATCH /api/purposes/{id}`) or closed but never removed. **Side finding, same shape:** a pass-through purpose is created by `a.queries.CreatePurpose` directly and has no delete route either, yet #633 lists it among the "config and deletable" routes. It moves no money, so it stays unkeyed, an accepted risk (Consequences).
3. **Reconciliations belong, and the cost is more than a second snapshot.** `Ledger.TakeReconciliation` (`internal/ledger/reconciliation.go`) has nothing to stop a repeat. Spiked per resolution, repeating the identical request: `matched` and `left_open` post a **second snapshot** (1 to 2) and move no money; `adjusted` is refused by itself, because the first plug moved the recorded figure, so the repeat's difference is 0 and `ErrReconciliationPlugMismatch` fires; **`entry_added` posts the fix a second time** (transactions 2 to 3, the fund 950 to 900) and stores a line with difference 0 and a fix of 50, which reads as an open gap of 50 that was not there (the spike finds one open line afterwards). `entry_added` imposes no amount check on purpose (a fix may close part of a gap), which is why nothing refuses it.
4. **A location opened with a starting balance is not deletable, and a repeat duplicates the money, so `POST /api/accounts` is keyed.** `POST /api/accounts` goes through `Ledger.CreateAccount`, which posts the `kind='opening'` row in the account's own transaction (#230). `account` has no uniqueness on its name (`dues_tier` has `UNIQUE (fund_id, name)`, so a repeated tier is a 409), so a repeat writes a second account and a second opening row. Spiked on a scratch copy of HEAD: a repeat of a Rp 500.000 opening took the fund from Rp 500.000 to Rp 1.000.000 (with the key, the repeat returned the first location and the fund stayed at Rp 500.000, and a create with no balance replayed the same way); `DeleteAccount` on the duplicate was refused by the foreign key from its opening row (787), and retiring it by `ErrAccountHoldsMoney`. The way out is an adjusting `out` entry of the amount on the duplicate and then retiring it, which leaves a retired location with two rows for good. #633 listed accounts among the "config and deletable" routes; that holds for an account with no starting balance only, so the create is keyed (On the wire). Outside the original seven it was the only write that moves money and has no guard against a repeat: the settle, reversal, close, setup and register routes are once-only, a repeated dues tier is a 409 by name, a repeated rate is a 409 or writes nothing and a repeated member-tier statement writes nothing (ADR-040), and the other creates (a member, a claim, a receipt) are deletable or move nothing.

## What was weighed and refused

- **A transaction opened by the HTTP layer around the ledger call.** Hangs: the ledger's `BeginTx` waits for the connection that wrapper holds (ADR-027), and so would the handler's own `resolveFund`.
- **Recording the key after the commit, or reserving it first and completing it later.** A crash between the two leaves a committed write with no key, or a key with no outcome that nothing can answer. The decided rule is one transaction.
- **A nullable `idempotency_key` column on `transaction` and the other tables.** Above: one of the several tables these routes write, never removed, in the backup, and no way to name a multi-row write.
- **Recording ids and rebuilding the reply on replay.** Per-route read code (the reconciliation's detail alone is a second query), and an answer that reflects today's rows rather than the original, which an envelope's mutable fields would make visible.
- **Storing the HTTP reply (status and bytes), built inside the transaction by a function the handler hands in** (a "seal"). It works; the four reasons against are in the Decision, and two facts belong here. A stored status is an `INTEGER` column that the schema audit `TestEveryMoneyColumnIsListed` (`internal/db/amount_ceiling_test.go`) reads as an unlisted money column (spiked: it fails naming `idempotency_key.status`; the table has only `created_at` and `expires_at`, both timestamps). And a stored domain value is easily set aside because sqlc emits no JSON tags (`emit_json_tags: false`), which is a reason against replaying one as the wire body and none against decoding it back into its struct and mapping it.
- **Server-issued keys.** A round trip to the connection that has just failed.
- **A key without a fingerprint.** A reused key with another body would replay the wrong result without a word. The fingerprint is what makes the 409 possible.
- **A raw-bytes body hash.** Safe, but a spurious 409 for any retry that is the same request in other bytes.
- **Keeping the remembered key in `sessionStorage` or IndexedDB.** It would survive a reload, but it turns the client into a small durable store ADR-008 declined and widens the window in which a deliberate second entry can be taken for a retry.
- **A key per form instance.** Contradicts the decided uniformity: the wrapper, nothing per form.
- **Recording refusals under the key.** A 409 today may be a success tomorrow (an envelope reopened); the retry should be judged afresh.
- **A pending state and a 409 or 425 for a concurrent twin.** There is no window in which one exists (above).
- **A ticker, or #608's hourly compare-and-swap sweep, for the purge.** Neither is needed once the purge rides the write (Retention). ADR-013 does not forbid a ticker; it chose one for the daily dump.
- **Requiring the header on the keyed routes.** Breaks curl, e2e seeding and an old cached bundle for nothing; a missing key is only an unprotected write.
- **Retention without end, or 7 days.** Without end, a table that only grows; a week keeps a world that has moved on able to answer. 24 hours covers a night without signal, and the client forgets after 15 minutes anyway.
- **Keying only the create-with-opening on `POST /api/accounts`.** The server's behaviour would depend on the body, and the case it leaves out, a create without a balance, is harmless to replay (On the wire).
- **A uniqueness rule on a location's name** (as `dues_tier` has `UNIQUE (fund_id, name)`) as the cure for a repeated create. It turns a repeat into a 409 the treasurer would meet, for a case a key handles silently.
- **Keying pass-through purposes.** A duplicate titipan is permanent, since no route deletes a purpose, but it moves no money and can be renamed; keying it would move its create from direct CRUD into the ledger (as `CreateAccount` did) for a tag. Left unkeyed, an accepted risk (Consequences).
- **Dropping remembered keys on navigation, or per form.** Resetting on navigation would protect the rare case, a deliberate identical second entry, at the cost of the common one, a retry typed again after leaving the screen; a reset per form is excluded by "nothing per form".
- **Telling the treasurer that an answer was a replay.** There is no toast surface and #634 touches no form. `Idempotent-Replayed` and the log line's age are there for a later line, if a real instance shows the merge below.

## PRD §4 check

No new screen, no setting, no dependency (the standard library's `crypto/sha256` and `encoding/json`, the browser's Web Crypto), and no concept the treasurer meets: she never sees the word key, and the app's copy does not use it. The one new thing is a table, the same class as `session`: plumbing for a running server, outside the backup. The PRD does not ask for it by name; it is PRD §5's "the numbers always add up" and goal 4, reliable enough to be the sole record, reached by CLAUDE.md rule 3's "corrections are new adjusting entries" for a case where today's only repair is a hand-made pair. The maintainer ruled it in scope on those merits (2026-10-19). Nothing in the non-goals is approached; the closest neighbour is rule 4's "no write queue", and this is its opposite: the wrapper never re-sends a write on its own, only when the treasurer taps again. The eighth route (a location) approaches nothing either: Tambah lokasi already exists, the key is invisible to her, and the route's only addition is the field. One element is not strictly required: the `Idempotent-Replayed` header, which no screen reads. It costs a line and lets a test or `curl` tell a replay from a first success without comparing rows, and it stays.

## Terms

**Idempotency key** is the nonce a client sends in `Idempotency-Key`; the **idempotency record** is the `idempotency_key` row (key, fingerprint, the stored result, expiry); the **fingerprint** is the hash that says whether a repeat is the same request; a **replay** is answering a repeat from the record; a **keyed route** is one of the eight, every other write is **unkeyed**. "Retry" is the treasurer's act and "replay" the server's; "token" stays `session`'s word, and "cache" is kept out of prose and code, because nothing here is a cache the system may drop. `CONTEXT.md` gets no entry (a transport mechanism the treasurer never meets; settled at approval), and **no Indonesian word is decided here**.

- **Tests.** Go: a replay per route (and the multi-period dues one; a location created with a starting balance, which must leave one `opening` row and the fund's balance unchanged by the replay, and one created without) whose result equals the first by value (`reflect.DeepEqual`, which is also the round trip of each stored type); the mismatch 409; the fingerprint (key order and whitespace equal, a number's text and the path's `{id}` different); the retention boundary (`expires_at` equal to now is expired), an expired row of the same key not tripping the primary key, and the purge removing every expired row; absent header unkeyed, malformed header 400 on a keyed route only, header ignored on an unkeyed one; the crash-between test; N concurrent requests on one key (under `-race`); restore clears it and the backup omits it; `uruni rebuild` starts empty; a file without the table refused at boot. Vitest: the key lifecycle (reuse for a twin and after a lost response, dropped on 2xx and 4xx, kept on any 5xx including a bare 502, an older twin's late failure not re-arming a spent key, forgotten at 15 minutes, never for `FormData`, `Content-Type` preserved, none on GET). One e2e journey: a lost response, then Simpan again, makes one row. Catat disables Simpan while a write is in flight, so a double tap cannot be driven; the test lets the request reach the server and then drops its answer (`page.route`, `route.fetch()`, then `route.abort()`), which `setOffline` cannot do, since an offline request never arrives. `web/e2e/COVERAGE.md` rows in both slices.
- **Docs, by their owners.** `docs/Decisions.md` (the eight keyed routes, the location finding, the pass-through risk; the orchestrator's). `PRD.md` section 7.2's connectivity bullet could gain a line, mirrored in `PRD-ID.md` and the maintainer's to word, but not "a save whose answer was lost is safe to repeat": that holds for 15 minutes after the last attempt and not across a reload. The claim the system keeps is that tapping Simpan again right after a lost answer does not record it twice. Leaving the PRD alone is also sound, since this is plumbing for section 5's "the numbers always add up". The ADR index gains this ADR's row (the orchestrator's). This ADR's tag came off with #635, the last slice that built it.
- **Accepted: a replay answers what happened then, not what is true now.** A repeat of a correction whose answer was lost, made after the same row was corrected again, returns the first correction's result while the row sits elsewhere. It is the merge below in another form (an identical request reuses its key whatever happened in between), it needs a lost answer and then two more corrections of one row inside 15 minutes, and it misleads about attribution only: a purpose correction moves no balance in any month.
- **Accepted: the one merge.** If a save's answer is lost, the first did land, and she then deliberately enters an identical second one within 15 minutes, the second is taken for the retry and not made. Only a lost answer sets it up, the replay is itself a definite answer and drops the key, so it happens once, and Riwayat shows the one row; the missing amount reads as a gap at the next *cek kas*.
- **Accepted: a reload forgets the key**, and the old advice (look first) stands for that case; the approved line does not contradict it.
- **Accepted: a duplicate pass-through purpose.** A lost answer to the Titipan form can leave two purposes of one name. No route deletes a purpose, so the second stays, appears in the purpose lists and can be renamed, and moves no money. The create stays direct CRUD (finding 2).
- **Accepted: 24 hours of results sit in the database file.** Small, outside the backup, and in the raw pre-upgrade copy as sessions are. Nothing logs a key or a body.
- **Accepted: a tightened check can refuse a retry** of a write that had succeeded, if a release between the two hardens argument validation, or the fund's zone moves west inside the window (above). The live instances' upgrade restores a backup, which empties the table.

## Settled at approval (2026-10-20)

- **`POST /api/accounts` is keyed, which makes eight keyed routes.** Locations were on the maintainer's unkeyed list of 2026-10-19; finding 4 is why they left it. The rule is the route's and not the body's: every create is keyed, with a starting balance or without, because a replay of a create without one is harmless and a rule that read the body would be more code for no gain (On the wire). `CreateAccount` takes the `Idempotency` field, and #635 carries it. The rest of the location routes stay unkeyed.
- **The record stores the ledger's result, not the HTTP reply.** No seal function, no `status` column, no replay carried as an error; a replay is the method's return value with a flag beside it. Spiked on a scratch copy of HEAD: a replay equals the first result by value, an insert the table's `CHECK` refuses rolls the write back, 20 concurrent twins post once under `-race`, and a read through the pool inside the transaction runs to the request's deadline.
- **Definite is a 2xx or a 4xx; any 5xx keeps the key.** A key kept across a refused request costs nothing, and a 500 does not prove that nothing committed.
- **Expired rows are purged in the miss path of the write's own transaction.** This replaces the hourly compare-and-swap sweep that #633 leaned towards, and takes the sweeper's state, its failure path and its tests with it.
- **Pass-through purposes stay unkeyed**, an accepted risk (finding 2). They move no money.
- **No replay UI in v1.** `Idempotent-Replayed` and the log line's age are there for a later line, if a real instance shows the merge.
- **The client forgets a key 15 minutes after its last failed attempt.** The merge is the general rule (an identical request reuses its key whatever happened in between) and the 15 minutes is what bounds it.
- **Copy:** the line under Copy, "Koneksinya terputus sebelum Uruni sempat menjawab, jadi belum pasti tersimpan. Cek dulu apakah sudah tersimpan sebelum menyimpan lagi." The sweep for "apakah" stays with #634 and #635 when it lands.
- **No `CONTEXT.md` entry.**
- **The grill's additions are accepted:** an older twin's late failure cannot re-arm a spent key; the wrapper exports a reset for tests; the e2e journey is a lost response followed by a retry, not a double tap; ADR-004's single connection is named as what serialises twins (`BEGIN IMMEDIATE` if the writer/reader split lands); argument-shape validation counts the clock and ADR-041's zone; the fingerprint is over the request path, not the route pattern; the replay log line carries the record's age; ADR-013 is cited for what it says (it permits a ticker); and PRD section 7.2 gets no "safe to repeat" line.
