# ADR-040 - Effective-dated tiers, and rate corrections that leave a trail

**Status:** Proposed · `draft` - drafted 2026-10-20 ([#621](https://github.com/kerti/uruni/issues/621), epic [#523](https://github.com/kerti/uruni/issues/523)) grilled and approved by the maintainer the same day; the tier half is built ([#624](https://github.com/kerti/uruni/issues/624)), the rate-correction half ([#625](https://github.com/kerti/uruni/issues/625)) and the screens and copy ([#626](https://github.com/kerti/uruni/issues/626)) remain, so it stays `draft` and editable in place, with any edit to a built part riding in the PR of the code that makes it true · supersedes [ADR-024](./024-schema-conventions.md) on one paragraph, named at the foot · [ADR index](./README.md)

**Context.** A dues month is priced by two lookups: which tier the member is in, and which rate that tier carries. The rate is already effective-dated (`dues_rate`, one row per start month, the latest at or before the period wins). The tier is not: `member.tier_id` holds only today's tier, and `DuesStatusForPeriod`, `OutstandingDuesForMember` (and `ArrearsMonthsForMember` on top of it), `paidThrough`, the roster's `tier_name` and `current_rate`, and the report's tier column all read it for every period. Promote a member in June and January is owed, shown partial or paid, and chained into arrears and into "Sudah dibayar sampai" (paid through) at the June tier. ADR-024 accepted this ("5-20 people with roughly annual tier changes ... revisit only if a real instance disagrees"), and two tests pin it: `TestDuesStatusForPeriodMidYearPromotionAppliesCurrentTierToPastPeriodsAcceptedLimitation` and its `OutstandingDuesForMember` twin.

The rate side has a quieter version of the same defect. `PATCH /api/dues-rates/{id}` overwrites the amount in place, and `DELETE` destroys the row (the code's own reason for it: it is what makes a rate filed against the wrong month correctable). Both silently reprice every period the rate covers, with nothing left to say it happened. The code calls this deliberate, and it is: the alternative is a wrong number nobody can fix. What is missing is the trail.

No live instance disagrees yet: no member on either has changed tier since joining. The reason to act now is the calendar. The schema is one file edited in place until `v1.0.0` (ADR-025), and #523 batches every schema edit into one migration dance on each live instance. After `v1.0.0` the same fix is a frozen-migration step on production data. Both defects share one cause - the thing priced is looked up as it is today, not as it was - so one rule fixes both. Drafted for the grill; no code exists.

## Decided before the grill

Recorded as decided (maintainer, 2026-10-19); not reopened here.

- **Backfill.** One `member_tier` row per tiered member, carrying the current tier from the month of `joined_on`. An untiered member gets no row. The earliest row reaches back to `joined_on`, so backdating `joined_on` for live arrears (PRD §7.1) keeps working. No member on either live instance has changed tier since joining, so there is no post-upgrade correction step.
- **Backup format.** `format_version` bumps to 2 **once for the whole epic**, at the tier slice (#624). The rate-correction slice (#625) edits v2 in place, because v2 never ships before the epic merges. The v1 to v2 step lives in `ParseUpload`, so `uruni rebuild` and the in-app restore both take v1 files, and the in-app restore shows its button for any version the importer can upgrade. ADR-012's "no restore button for older-format backups" line is edited in #624's PR, with its code; this ADR does not touch ADR-012.

## Decision

**A start-dated row holds from its month until the next row's month, and a mistake in one is corrected by a new row, never an overwrite.** That is the whole rule, applied to both series: `dues_rate` (a tier's price) and the new `member_tier` (a member's tier). Two verbs, kept apart because they do different things to the past:

- A **change** adds a row at a month that has none. It touches no period before that month; backdated, it reprices the months from there up to the next row, which is how PRD section 7.1's live arrears are opened.
- A **correction** replaces what a month said. It deliberately reprices every period that month's row covers - a mistyped amount was never the truth - and it leaves the superseded row behind.

Nothing posted moves: a correction changes what is *owed*, never what was *paid*. No balance moves and reconciliation is untouched. Months are the only grain (a change takes effect for its whole month, as dues are one monthly amount, never pro-rated).

**The shape of a correction: a number within the month.** Both tables gain `correction INTEGER NOT NULL DEFAULT 0`. The first row stated for a month is `0`; each correction of that month is the next number; **the highest number stands** and the rest are superseded. `UNIQUE (tier_id, effective_from)` becomes `UNIQUE (tier_id, effective_from, correction)` - so a month always has exactly one standing row, and the schema, not a trigger or a pointer to police, is what says so across any number of corrections. The next number is read and written in one transaction (ADR-004's single connection; the `UNIQUE` is the backstop). Ordering is by `correction`, never by `created_at` or `id`.

**`member_tier`: the member's tier, month by month.**

```sql
CREATE TABLE member_tier (
  id             INTEGER PRIMARY KEY,
  fund_id        INTEGER NOT NULL,
  member_id      INTEGER NOT NULL,
  tier_id        INTEGER,                -- NULL = no dues obligation from this month
  effective_from TEXT    NOT NULL,       -- 'YYYY-MM', dues_rate's CHECK incl. the 2000-01 floor (#632)
  correction     INTEGER NOT NULL DEFAULT 0 CHECK (correction >= 0),
  created_at     INTEGER NOT NULL,
  UNIQUE (fund_id, id),
  UNIQUE (member_id, effective_from, correction),
  FOREIGN KEY (fund_id, member_id) REFERENCES member(fund_id, id) ON DELETE CASCADE,
  FOREIGN KEY (fund_id, tier_id)   REFERENCES dues_tier(fund_id, id)
) STRICT;
```

A sketch of the shape, not the migration text: #624 owns that. One-sided month rows exactly like `dues_rate` (no `effective_to`: gaps and overlaps are inexpressible, which is the point of `dues_rate`'s own comment). Composite fund-scoped foreign keys on both pointers (ADR-024); a `NULL` `tier_id` passes the composite, as on `member` today. **`member.tier_id` is removed** and the current tier is derived, because a column kept "as a cache" would be a second source of the same fact that a restore or a half-done write could leave disagreeing with the rows.

- **Reading.** A member's tier at period P is the tier on the row that stands for the latest month at or before P. No such row, or a `NULL` tier, means no obligation (never shown as unpaid). The **current tier** is the tier at the current month, or at the join month if that is later (a member who joins next month shows the tier entered for them, as today), **read in the fund's time zone** ([ADR-041](./041-the-funds-time-zone.md), [#638](https://github.com/kerti/uruni/issues/638)), not Asia/Jakarta; until #639 moves every month read, #624 reads `tz.Jakarta` like the rest. The wire `tier_id` on a member stays the current tier, with one exception: a `GET /api/dues-status` row carries the tier at the requested period, the one that priced its `owed_amount`, because the report prints it and a row must not show a tier beside an amount that tier did not set. Rows for a whole page or fund are fetched once and folded per member, so no read adds a per-member query (#624).
- **Writing is "from a month".** The Anggota edit form gains **Mulai bulan** beside the tier, defaulting to the current month (fund's zone), or the join month if that is later. The treasurer never addresses a row, because she cannot see one (below): she states what is true from a month, and the engine decides whether that is a new row or a correction.
  - A month with no row for this member: a new row (a change).
  - A month that already has a row: the next `correction` of it. This is how a wrong tier or a wrong month is fixed - state the right one - with no extra control. A wrong start month needs nothing special: state the tier from the right month; if the wrong month's row now says something the timeline should not, state that month again.
  - A save whose tier is already the one read at that month writes nothing, so re-saving the form leaves no stray rows. It also means a statement does not cancel a later row: with A from January and B from June, "A from March" changes nothing, and undoing the promotion is "A from June".
  - Choosing no tier is a row with `tier_id` `NULL` from that month.
  - The start month is refused (the typed date error of #632, not a new code) before the member's join month, and **after the current month** (or the join month, if that is later). See the ceiling below.
- **Join date moved earlier.** `PATCH` of `joined_on` to a month before the member's earliest row appends a row at the new join month carrying that row's tier (when it has one), provided that row starts at or before the old join month. "At or before", because a join date once moved later leaves the earliest row ahead of the join month. This is "the earliest row reaches back to `joined_on`" held as an invariant by the writer, and it is not optional: without it a live-arrears backdating (PRD section 7.1) would open months in which the member has no tier and owes nothing, with nothing on the form to say why. If the earliest row began *after* the old join month (a member untiered at first), the longer untiered stretch is left untiered. `POST /api/members` and Setup write the first row at the join month (the current month by default) when a tier is given, and no row when it is not. That row is bounded by the join date's own ceiling (#632), not by the tier-start ceiling below.
- **Deleting a member** (setup duplicates only) takes their `member_tier` rows with it, by `ON DELETE CASCADE`, as `incidental_recipient` does. Unlike that table, whose rows are "a choice, not a record", these rows are a record; the cascade is safe because a member any posted row names is still refused by the ledger's foreign keys, so no month anyone paid is ever cascaded away.

**Ceiling for a tier start: the current month (or the join month, if that is later).** A tier chosen on the edit form cannot start in a future month. A future row would be a pending change that Anggota does not show (it shows the current tier) and nothing lists (see below), and it silently becomes current on the first of a month; backdating is supported, so nothing is lost by entering the change on or after the month it takes effect. A rate keeps #632's ceiling (current month + 24) because a pending rate *is* shown, in the Golongan screen's list; the asymmetry follows from where each can be seen. *This departs from #632's parenthetical "(and a tier's start month)"; the maintainer chose it at approval (2026-10-20), and #632 is edited to match.*

**`dues_rate`: the same two columns, and a delete that records.**

```sql
-- dues_rate gains:
correction INTEGER NOT NULL DEFAULT 0 CHECK (correction >= 0),
deleted    INTEGER NOT NULL DEFAULT 0 CHECK (deleted IN (0, 1)),
CHECK (deleted = 0 OR correction > 0)                -- only a correction can delete
-- UNIQUE (tier_id, effective_from)  ->  UNIQUE (tier_id, effective_from, correction)
```

- **The rate at period P** is: take the standing row of each month at or before P, drop the months whose standing row is a deletion, and take the latest month left. No month left means no rate decided (the "madya TBD" case: the period is skipped, never invented).
- **`PATCH /api/dues-rates/{id}`** (amount only, as today) appends the next `correction` for that month with the new amount; an amount equal to the standing one writes nothing. It reprices the periods that row covers - from its month to the next month that still has a rate - and nothing else. No age limit and no payment guard.
- **`DELETE /api/dues-rates/{id}`** keeps its verb and its place in the screen and appends a **deleting correction** (`deleted = 1`), copying the amount it withdraws. The month then holds no rate, and the periods fall back to the earlier month's rate or to "not decided". This is what makes an erroneous *first* rate removable; restating a later month to the earlier amount would reach the same reads for any other row, but a deletion keeps the visible list free of redundant rows.
- **`POST` into a month** whose standing row is a rate still answers 409 `unique_violation` (the existing code and copy); into a month whose standing row is a deletion it appends the next `correction`, so a deleted rate can be re-added.
- **A wrong-month rate** is corrected the way the screen already does it: delete the row at the wrong month, add one at the right month. That answers how `UNIQUE` survives a correction: the delete, and any later re-add at the *same* month, are further numbers of one month and never collide. No verb moves a row, and `PATCH` carries no `effective_from`.
- **`GET /api/dues-tiers/{id}/rates`** lists the standing, non-deleted rows, oldest month first, so the client's existing fold ("latest at or before") is unchanged. A row's id changes when it is corrected, because a correction is a new row; PATCH and DELETE on a row that no longer stands are refused rather than applied to its successor.
- The ceiling (#499) and the schema's amount `CHECK`s (#622) apply to a correction as to any rate. Because the new rows are written by a read-then-insert, rate writes move from direct CRUD into the ledger (ADR-027).

**Immutability: a trigger against UPDATE on both tables; no trigger against DELETE.** `member_tier` and `dues_rate` each get a `BEFORE UPDATE` trigger that aborts ("a correction is a new row"), in ADR-024's style: a convention is what let `PATCH` reprice history. No `BEFORE DELETE` trigger, deliberately, which is a step short of ADR-024's pair. Three paths delete these rows: a member's deletion (the cascade), a never-named tier's (`DeleteDuesTier`) and restore's clear-all. A `WHEN` clause can tell the first two from a stray delete (checked: in a cascade the parent is already gone), but a guard would make restore's clear-all depend on the order it deletes in, or grow `immutableTriggers` and its drop-and-recreate. The owners' foreign keys already do the work: a member named by any posted row, and a tier named by any `member_tier` row, cannot be deleted. The HTTP route that destroyed a rate is gone, and a test fails if any query other than `DeleteDuesRatesByTier` and restore's clear-all deletes from either table, so the convention is held by something that runs.

**Visibility: the existing fields, and no list.** The treasurer sees a member's current tier and rate on the roster, the dues status and, per month, the report's **Golongan** column and owed amounts; she edits it through **Mulai bulan**. There is no tier-history list, no "as of" selector on Anggota, no "diperbaiki" marker. The trail lives in the data and the backup, not on a screen. Errors surface where she already looks: the owed amount in a month, or that month's tier in the report. The Golongan screen's rate list is unchanged in shape.

**Terms.** `member_tier` is the identifier (English, ADR-024). **Mulai bulan** ("from month") is the copy for a start month, for tiers and rates alike, and `effective_from` is its identifier on both tables. **Correction** is ADR-033's word, and `correction` the column; "Perbaiki nominal" ("correct the amount") is its existing copy, "Hapus tarif" ("delete the rate") the existing copy for the delete. **Golongan** ("tier") and "Tanpa golongan" ("no tier") are the existing words for a tier and for none; "Sudah dibayar sampai" ("paid through") is the existing copy for `paidThrough`, and "lunas sampai", which appears only in a code comment, is not a label. The issue's shorthand "membership row" means a `member_tier` row; "membership" alone is not used, because `member` with `joined_on` and `inactive_on` already says who belongs to the fund. "Standing" names the row that wins within a month and is not an identifier; it is the move ADR-033 and #627 call "effective" (an "effective purpose" is the latest correction's), spelled differently here only because `effective_from` has already spent "effective" on the month axis, where it stays for "in force for a period". What `DELETE` appends is a **deleting correction** (`deleted = 1`); "tombstone" is the usual word for it and is kept out of prose and code. **No new Indonesian word is decided here.**

## What was weighed and refused

- **A guard: refuse a rate edit once a dues payment exists in a covered period.** Fails closed in the one case that needs the fix. A rate mistyped 500.000 for 50.000 is noticed *because* members paid 50.000 and everyone reads partial, so a payment already exists and the guard forbids the repair; the wrong number then stands for every past month. It also leaves no trail for the edits it does allow.
- **A pointer column** (`corrects_rate_id`, as ADR-033's `corrects_transaction_id`). Every read would need "no row corrects me", and one live row per month would need a trigger, because a partial index cannot see another row. The number within the month gives the same supersession with a plain `UNIQUE`. Its cost is that a correction cannot change its month, which the screen's delete-then-add already handles.
- **Bitemporal "as known at" reads.** Every dues read would take a second time axis, and a public report month would need a notion of when it was read. Nobody has asked to see a month as it once read; correction exists so that it reads right. Append-only rows keep `created_at`, so the data does not foreclose it later. Too heavy now.
- **A correction that carries its own month** (move a row in one step). A second input on a verb that today takes one, to save two clicks a treasurer rarely makes.
- **Overwrite in place with a "previous value" column.** Holds one level of history; a second correction erases the first.
- **`member.tier_id` kept as a cache of the current tier.** Two sources of one fact (above).
- **A tier-history list on Anggota.** A new screen or section for a state the roster, dues status and report already reveal month by month; PRD §4.
- **A future tier start up to +24 months.** See the ceiling above.
- **`BEFORE DELETE` triggers, or `amount` made nullable for the deleting correction.** The first can tell an owner's deletion from a stray one, but makes restore's clear-all order-dependent or grows `immutableTriggers` (above), so a test guards the convention instead; the second overloads a money column, and `NOT NULL` keeps every `rate.Amount` an `int64` for sqlc and the ceiling `CHECK`.

## PRD §4 check

No new screen (Anggota's edit form gains one existing-word field; the Golongan screen's two verbs stay where they are). No setting. No dependency. No concept the treasurer meets: her words stay golongan, Mulai bulan, perbaiki, hapus. The internal ones - `member_tier`, the correction number - are the fix itself, and the second is ADR-033's word. Nothing in the non-goals is approached: no accounting journal, no analytics, no reminders. The bitemporal option, which is the accounting-package direction, is the one refused for that reason.

## Consequences

- **Every dues read changes in one place.** `DuesStatusForPeriod`, `OutstandingDuesForMember`, `ArrearsMonthsForMember`, `paidThrough`, `ListMembersPage` (`tier_name`, `current_rate`) and the report's dues table take the tier at the period. The standing-row rule is defined once in the schema (a view per table, in the manner of #627's ledger views) and every read selects from it. sqlc types such views usefully (spiked in the grill on v1.31.1: plain-column views come out as `int64` and `*int64`, and the roster's `LEFT JOIN`s over them keep their nullable columns nullable). A guard test, as #627 has for the ledger views, fails when a query reads `dues_rate` or `member_tier` other than through the view; the backup export (every row, superseded and deleted ones included), the by-id lookup that `PATCH` and `DELETE` start from and the read that picks the next `correction` are the named exceptions. It is not tidiness: the obvious query, dropping the deleted rows first and then taking the latest, still finds a deleted month's own earlier row (Jan 50.000, Jun 70.000 then deleted, read at June: 70.000 instead of 50.000; checked). The two pinned limitation tests are replaced by their opposite: January stays at the old tier. Ledger participation (ADR-034) reads no tier and is unaffected.
- **The report and PDF show each member's tier as of the selected month**, not today's. The page and the PDF render the same assembly (ADR-035).
- **`DeleteDuesTier` and Decisions.md.** "A tier no member is in priced nobody" stops being true: it was true only because a tier held no past. The rule becomes "a tier no member has *ever* been in", and the foreign key from `member_tier` enforces it with no new code, because a row is never deleted while its member exists: a tier any row names, even a superseded one, is refused (409 `referenced_by_other_records`) and the transaction rolls back the rate deletion, as today. The surviving case - a setup typo nobody was ever put in - still deletes with its rates. Accepted cost: a tier a member was put into by a slip, since corrected, can no longer be deleted; rename it. The Decisions.md sentence and `DeleteDuesTier`'s comments need the word *ever* (maintainer's surface), and so does the refusal the treasurer reads: "ganti golongan mereka dulu" ("change their golongan first") is advice that stops working, because the old rows still name the tier. Its copy is rewritten in #626.
- **Backup and restore.** v2 gains a `member_tiers` array, drops `members[].tier_id`, and gives each `dues_rates` entry `correction` and `deleted`. Both arrays carry every row, superseded and deleted ones included: the trail is the data, and an export of standing rows only would lose it on the first restore. The v1 to v2 step makes one `member_tier` row per tiered v1 member (`correction` `0`, from the month of `joined_on` - or, for a pre-#471 file with a null one, the fund's adoption date, as restore reads it today - `created_at` taken from the member's own, ids in member-id order) and reads a v1 rate as `0`/`0`. Restore inserts `member_tier` after `member` and `dues_tier`. **`immutableTriggers` does not grow**: it names the triggers that fire on restore's own deletes and inserts, restore only inserts and deletes these tables, and an `UPDATE` trigger never fires there. Each new trigger still gets its own refuses-an-update test. The v2 golden carries a corrected rate, a deleted one and a member with a superseded tier row, so the round trip proves the trail survives. ADR-012 is edited in #624's PR; `TestRebuildTakesThePreviousReleasesBackup` stays the proof that v1 reaches v2 and totals.
- **Proof the backfill is neutral.** Status, owed, paid, arrears and paid-through for every member and period must be identical between a test helper reproducing the legacy current-tier rule and the new engine. The v0.9.0 golden is two members, one tier and one rate, so it proves little alone: the comparison also runs over a v1 file built to hold a rateless tier, a tier-less member, an inactive member, a late-starting rate, a backdated rate and a prepaid run, and the maintainer's `make upgrade-rehearsal` on both real backups ([#636](https://github.com/kerti/uruni/issues/636)) is the proof on real data. New tests: past partial/paid status, the arrears chain, paid-through across a tier change, tier removal, a change in the joining month, a backdated `joined_on` with live arrears (also after the join date was once moved later), a member who joins next month, a rate correction, a deleted first rate, a deleted later rate falling back to the earlier one, a delete-then-add at a new month, a re-add at the same month, a `PATCH` or `DELETE` of a superseded id refused, and a tier named only by a superseded row refused for deletion.
- **Accepted: a correction reprices the past, at any age.** A month a public reader has already read can read differently afterwards - a Lunas becomes Bayar sebagian, or the reverse. It is the exposure ADR-033 accepted for attribution, one step larger, since it moves a status; the ledger and every balance are untouched. The confirmation for "Perbaiki nominal" must name the span it reprices (from the corrected month to the next month that still has a rate). The sentence is new copy and is proposed to the maintainer before it lands (#626).
- **Accepted: the history is data, not a screen.** A stray old `member_tier` row is found through the report's per-month tier and the owed amounts, and fixed by stating its month again.
- **Accepted: a tier raise lands on prepaid months** - a month paid in full at the old tier reads partial, and `paidThrough` ends before it - exactly as a rate raise already does ("reads honestly as not paid through").
- **Member writes join the ledger.** `POST` and `PATCH /api/members` (the first row, the join-date rule, "from a month", the no-op check) and the e2e seed write a member and its `member_tier` rows together, and read before they write, so they leave direct CRUD for the ledger with the rate writes (ADR-027). That ADR's sentence "member CRUD carries no derived invariant beyond what the schema already enforces" stops being true for the tier and the join date; its decision, one package, stands, so the fix is an amendment, made in #624's PR with the code.
- **Not changed: the window.** `joined_on` and `inactive_on` still move whole months in or out of what is owed without leaving a row. They are dates the treasurer states, not prices, and this ADR fixes prices.
- **A restatement that equals the earlier tier leaves a redundant row.** Harmless to every read.
- **Copy and docs, by their owners.** The Pengaturan body ("bukan menimpa yang lama ... supaya bulan-bulan lampau tetap terbaca dengan tarif yang berlaku waktu itu") is true of a *new* rate and false of a correction; with "Perbaiki nominal" and "Hapus tarif", the refusal when a golongan is still used (above) and the confirmation for a correction (approved at approval; #626's criteria list it) it is rewritten in #626, after a sweep of CONTEXT.md, PRD-ID and `copy/id.ts`. PRD §6 ("Dues rate ... editable") and CONTEXT.md ("Dues rate", "Member") change in the epic close-out (#636). The schema changes with `make db-reset` for development and the backup-restore dance for the two live instances (ADR-025), once for the whole epic.

## Settled at approval (2026-10-20)

- **The future-start ceiling:** the current month, or the join month if that is later (above), not #632's current month + 24. A pending rate is shown in the Golongan list and a pending tier nowhere, and backdating makes entering a change in advance unnecessary.
- **The trail is data-only.** No marker beside a corrected rate; a stray row shows in the report's per-month tier and the owed amounts.
- **The grill's additions are accepted:** the current tier read at the later of the current month and the join month; the dues-status row carrying the tier at its period; reopened months taking the old join month's tier; the guard tests; and the "Perbaiki nominal" confirmation naming the span it reprices.

## Superseded in ADR-024

The paragraph **"Accepted limitation: `member.tier_id` is not effective-dated"** ("A member promoted mid-year has their *current* tier applied to past periods ... Revisit only if a real instance disagrees") is superseded: a member's tier is effective-dated, in `member_tier`, and `member.tier_id` is gone. The rest of ADR-024 stands, including "Lookup tables only for rows a user creates" (a tier is still a table the treasurer names) and the immutability-by-trigger principle this ADR applies to two more tables, `UPDATE` only. ADR-024's status line and that paragraph point here in #624's PR, with the code that makes it true.
