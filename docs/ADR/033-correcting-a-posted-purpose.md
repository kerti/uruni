# ADR-033 — A posted row's peruntukan can be corrected

**Status:** Accepted · implemented at M6 ([#267](https://github.com/kerti/uruni/issues/267) engine, [#276](https://github.com/kerti/uruni/issues/276) surface) · change only by adding a superseding ADR · [ADR index](./README.md)

**Context.** Transactions are immutable, and that is not in question here. What immutability is supposed to buy is corrections that are *cheap*: `CONTEXT.md` states it as a rule — *"Never edited or deleted — corrections are new adjusting entries."* For one correction the app does not keep that promise. A transaction tagged with the wrong **peruntukan** cannot be re-tagged at all.

The engine has had the operation since M3. `postTransferPairTx` (`internal/ledger/transfer.go`) takes two legs of `{AccountID, PurposeID}` and a kind, and `kind='reclass_purpose'` moves what money is *for* while leaving the fund total and every account balance untouched. Its only callers are inside `CloseIncidentalAndRoll`. No route reaches it, deliberately — `POST /api/transfers` takes a singular `purpose_id` because a `between_accounts` transfer never changes what money is for.

So the treasurer's only recourse is to hand-build the pair the engine would have built for her, on the same account and the same date: an `in` to the wrong tag, an `out` to the right one, equal amounts. Working that out is an accounting exercise, and this product's entire premise is a treasurer who is not an accountant and is already anxious about the numbers. She will also post both rows as `kind='normal'`, because `RecordTransaction.tsx` pins `is_adjustment` to false, so the ledger will not even record that the two rows were a correction. Found by the maintainer, in ordinary use, after tagging a levy payment `Titipan`; filed as [#267](https://github.com/kerti/uruni/issues/267) and grilled 2026-09-17.

**The framing that decides most of this: she never reclassifies.** "Reclassification" is journal vocabulary, and PRD §4 lists accounting journals as a non-goal. What she does is look at a row in Riwayat whose peruntukan is wrong and fix it. That is an existing noun and an ordinary verb, so no new concept enters the product — which is what the prime directive actually polices. `reclass_purpose` stays the identifier, in English, in the engine, where `CONTEXT.md` already puts identifiers.

The sibling issue ([#266](https://github.com/kerti/uruni/issues/266)) improves guidance at record time so the mis-tag happens less. That is worth doing and is not a substitute: guidance prevents the *next* mis-tag, while the one already posted stays wrong forever.

## Decision

**A posted row's peruntukan can be corrected, by posting a `reclass_purpose` pair that points at the row it corrects.** Never by editing the original row, and never through a second write path in `PostTransaction` — [ADR-027](./027-ledger-domain-boundary.md) keeps that method narrow.

- **The correction knows what it corrects.** `transfer` gains `corrects_transaction_id INTEGER`, nullable, with a composite `FOREIGN KEY (fund_id, corrects_transaction_id) REFERENCES "transaction"(fund_id, id)` like the six the ledger already carries. Null is a roll; set is a correction. The link buys three things a free-standing pair cannot give: the read-time label stops guessing, repeat corrections become answerable, and [#257](https://github.com/kerti/uruni/issues/257)'s rule that a row must explain itself can say *which* row this one fixes.

  It sits on `transfer`, not on either leg: the correction is the pair. And it is not `reverses_transaction_id` reused — [ADR-029](./029-reversing-a-dues-payment.md) nailed that column shut from both directions, because a stray setter hides the original from `DuesPaidByPeriod` and consumes the reversed-once slot.

- **One asymmetric `CHECK`, and it is deliberately weaker than ADR-029's.** `CHECK (corrects_transaction_id IS NULL OR kind = 'reclass_purpose')` — nothing but a purpose move may claim to correct anything. The mirror (a correction *must* set the link) is not enforced, which would require a third `transfer.kind`. That is refused because `transfer.kind` answers *what shape of value-neutral move this is* — `between_accounts` is where money sits, `reclass_purpose` is what it is for — and a correction is unambiguously the second shape. A third value would make the column answer "what moved" for two of its values and "why it moved" for the third. The damage from the unenforced half is proportionate to leaving it unenforced: a roll that wrongly set the link would mislabel one row in Riwayat. ADR-029 had to be absolute because its stray write corrupts a query.

- **The pair carries the original row's date, and the date is not a field.** The correction is not an event; it is a statement that the row was always meant to say something else. Dating it today would leave the month the mistake was made wrong in both tags — §7.9's report filters by month — while inventing an event in the current month that nobody performed: money leaving Titipan in September that no one moved. Both legs therefore take the original's `occurred_on`, read from the row and never offered as an input. The roll is not a counter-example: `CloseIncidentalAndRoll` dates on `ClosedOn` because a close genuinely happens on a day.

  This means a correction can change a month a public reader has already read. The ledger is untouched either way and no month's *balance* moves — only attribution, in the month where the misattribution happened — which is the same exposure [#264](https://github.com/kerti/uruni/issues/264) accepted for renaming, one step larger.

- **The "from" leg is the row's effective peruntukan, computed, never stored.** Correct a row once and its stored `purpose_id` is still the original tag forever, because the row is immutable — but the money is elsewhere. A second correction built from the stored tag would move money out of a tag that no longer holds it and drive it negative, which is the exact defect #266 reports, re-created by the tool meant to fix it. So the effective tag is derived by following the corrections pointing at the row and taking the destination of the latest. Same derive-don't-store move as [#270](https://github.com/kerti/uruni/issues/270): it is a fact the ledger already determines, and storing it would mean mutating an immutable entry.

- **The list keeps showing the stored tag, and the arithmetic forces this.** A corrected 250.000 expense leaves three rows in Riwayat: the original, and the pair's two legs. The ledger sums stored tags — Titipan −250k, then Titipan +250k and Kas Utama −250k — netting to Kas Utama −250k. If the original rendered its *effective* tag, a reader would see Kas Utama charged twice and Titipan credited once, and the screen would stop summing to the balances. "Balances are derived by summing the ledger" is the trust core; a screen that disagrees with it is worse than one that shows an old tag. The effective tag therefore lives in the dialog and in the ledger's own computation, and never in the list.

- **Eligible: `kind='normal'`, and `kind='adjustment'` where `reverses_transaction_id IS NULL`.** A reconciliation fix is mis-taggable in the UI today — `Reconcile.tsx` renders a full `PurposePicker` with Kas Utama as a default rather than a pin, while `Fix` deliberately has no `AccountID` because the account is derived. The purpose was left free where the account was pinned, which is what makes the slip reachable.

  Refused, each for its own reason and with its own named 409, never one blanket rule: **`opening`**, whose peruntukan is Kas Utama by construction; **`dues`**, where a tag bound to the dues concept is not a mis-tag to fix but a different entry; **`reimbursement`**, whose payout inherits the claim's peruntukan and whose correction already exists as Talangan's own `Perbaiki` — so the refusal names where to go; and **`transfer`**, because a leg is half a movement and correcting one alone breaks the pair's value-neutrality, the invariant the whole transfer design rests on.

  **The chain problem dissolves in that last refusal.** A correction's own legs are `kind='transfer'`, so a correction can never be corrected: no depth limit, no cycle rule, no special case.

- **A closed amplop is refused in both directions, and the refusal points at `reopen`.** `postTransferPairTx` checks nothing by design, so a correction route would walk straight through both of [ADR-031](./031-posting-to-a-closed-incidental.md)'s guarantees. Correcting *into* a closed envelope posts to a purpose that refuses postings; correcting *out of* one leaves its balance non-zero, breaking the single invariant that #270's derived rollover now reads. Both answer 409 and say what to do — *"Buka lagi amplop ini dulu"* — rather than refusing flatly. A correction that reopened the envelope implicitly would move money across a lifecycle boundary without her saying so.

- **The route is `POST /api/transactions/{id}/purpose-correction`, body `{ "purpose_id": N }`.** Addressed by the row it corrects, matching the nested-verb idiom `/api/incidentals/{purposeID}/close` already uses. One field in the body is what makes immutability structural rather than promised: there is no way to send an amount, an account or a date, so the route cannot edit the original row even by accident. It answers with the `transfer` row. `Ledger.PostPurposeCorrection` owns every rule above, including the no-op refusal when the target equals the effective tag; per ADR-027 the handler validates nothing.

- **`is_adjustment` stays confined to the reconcile flow.** #267 asked whether it should reach the wire from anywhere else. It need not: `postTransferPairTx` posts both legs as `kind='transfer'`, so a correction is never a `PostTransaction` and never touches `IsAdjustment`. The two `kind='normal'` rows the hand-built workaround produced are exactly what this route deletes.

- **The dialog, and the rule it sharpens.** [ADR-032](./032-two-level-navigation.md)'s table says a dialog "edits one row and posts no ledger entry"; this posts two legs. The rule is sharpened rather than bent, in ADR-032 itself: **a dialog may post only when the posting is value-neutral and carries a single field.** That readmits the opening-balance exception that ADR already states, and still refuses every money form — those carry five or more fields, a photo picker, smart defaults and a success handoff. The stated fear behind the original rule is "a posting dismissible by a stray backdrop tap", and a correction pair cannot move a balance in any month: the worst case of a stray tap is that no correction happens.

- **The peruntukan itself is the control.** Not the whole row: eligibility varies, and a tappable row would be a dead tap on a dues row and a live one on the expense beside it with nothing visible to tell them apart. Not a button either — the amount column is right-aligned and `tabular`, the column she scans, and a per-row button either breaks that alignment or adds 44px to every eligible row on the app's densest unbounded list. So the peruntukan text becomes the control, on the row's first line, being the exact noun it corrects, with padding for the 44px target and a dotted underline to read as tappable. Ineligible rows render it as plain text, which makes eligibility self-evident.

- **Two labels, one glyph, no new lines.** The correction legs reuse `transferPurpose`'s existing `from → to` text and change only the icon and the screen-reader word: `Tags` and `Perbaikan peruntukan`, against the roll's `Mail` and `Tutup amplop`. The original row gains a muted `Tags` after its peruntukan — the same glyph, which is what ties the row to the pair below it — with an `sr-only` *"Sudah diperbaiki"*, because the existing pattern hides icons from screen readers and carries the word separately. Nothing grows by a line.

## Consequences

**`copy.rowLabels.transferPurpose.kind` is the literal string `Tutup amplop`, and that was correct until now.** A `reclass_purpose` pair has had exactly one possible origin, so #257 could hardcode it. The first correction posted under this ADR would otherwise label itself as an envelope closing that never happened. This is the concrete reason the link is worth its column: the distinction is exact, rather than inferred from whether some incidental happens to be closed — which #270 already proved unreliable, since a reopened envelope keeps a past roll.

**Transaction rows become interactive for the first time.** `TransactionList.tsx` has no `onClick`, no button and no interactive role today; rows are inert. Once one affordance exists, the next feature will want one, and the honest answer is that a second action becomes a second control and a third earns a `(...)` menu — a menu holding one item is an extra tap and a hidden label for no gain. Where that pressure resolves is [#212](https://github.com/kerti/uruni/issues/212)'s information-architecture question, which inherits this precedent rather than meeting it cold.

**An icon teaches nobody the first time.** `Tags` beside a peruntukan is unambiguous once she has seen a correction and meaningless before that. Density on Riwayat is bought with first-encounter clarity, knowingly. Whether a dotted-underline chip reads as tappable, and whether a muted glyph is even visible at row scale, are questions only an iPhone answers — both need a device check before the tag comes off this ADR.

**Correcting a row inside a closed amplop is a three-step: reopen, correct, close again.** The second close re-rolls correctly with no new arithmetic, because `IncidentalTotals` sums every row against the purpose unfiltered and therefore computes the net delta — the property ADR-031 established and #215's fix preserved. It is more steps than she would like, and it is the price of ADR-031's zero-balance invariant staying true.

**The schema change costs a `make db-reset` for everyone.** One migration file through all of `0.x` ([ADR-025](./025-one-migration-file-until-1.0.md)), edited in place, so goose cannot see that a file it already applied has changed.
