# ADR-029 — Reversing a dues payment: a linked adjustment row, not netting

**Status:** Accepted · implemented at M4 — change only by adding a superseding ADR · [ADR index](./README.md)

**Context.** PRD §7.3 requires undoing a dues payment recorded in error — wrong member, entered twice — by reversing it with a new entry, never editing or deleting the original (`CLAUDE.md` rule 3), and the member must read as **unpaid for that period again**. The schema's two `kind='dues'` CHECKs make that second half impossible by construction: `CHECK (kind <> 'dues' OR (member_id IS NOT NULL AND dues_period IS NOT NULL AND direction = 'in'))` forces every dues row to name a member and a period and to flow inward, so a correcting outflow cannot itself be `kind='dues'` — and `DuesPaidByPeriod` / `LatestDuesPeriodPaidByMember` only ever read `kind='dues'` rows. Post the reversal any other way and it fixes `FundBalance` while the roster still shows the member paid: the recorded balance and the recorded status disagree, which is exactly the failure `CLAUDE.md` rule 2 and PRD §5 ("the numbers always add up, and Uruni proves it") exist to rule out. This is trust core, not a display bug — a stale "paid" reading is the kind of quiet error a reluctant treasurer has no way to notice on their own.

Filed as [#82](https://github.com/kerti/uruni/issues/82) and grilled 2026-08-26 alongside its sibling [#96](https://github.com/kerti/uruni/issues/96) — a multi-period dues payment posted as several separate inserts, so a retry after a partial failure can leave an orphaned duplicate `kind='dues'` row with no way to remove it from the status queries either. The two share a symptom, an unremovable dues-status artifact, but not a fix: #96 is a transaction-boundary bug in Go, closed by posting every period of one payment inside a single `withTx` behind a new plural `Ledger.PostDuesPayments`, no schema change, already merged. This ADR is the schema-touching half, and ships after it — sequenced so the atomic multi-period post is already in place shrinking the number of duplicate rows a pilot database can accumulate before reversal exists to clean any of them up.

## Decision

**One linked adjustment row, not a netting entry.** Reversing a dues payment posts one new `"transaction"` row — `kind='adjustment', direction='out'` — carrying a new nullable `reverses_transaction_id` that names the row it reverses. `account_id`, `purpose_id`, `amount`, `member_id` and `dues_period` are **copied from the original row by the ledger method**, never re-typed by the caller — the same discipline [ADR-027](./027-ledger-domain-boundary.md) already applies to `SettleReimbursement`, which has no `Amount` or `PurposeID` field for exactly this reason: a reversal that could name a different amount or member than the payment it reverses would not be a reversal of that payment.

Schema, following [ADR-024](./024-schema-conventions.md)'s conventions throughout:

- `"transaction".reverses_transaction_id INTEGER`, nullable.
- The second dues CHECK — today `CHECK (kind = 'dues' OR (member_id IS NULL AND dues_period IS NULL))` — gains one disjunct: `OR (kind = 'adjustment' AND reverses_transaction_id IS NOT NULL AND member_id IS NOT NULL AND dues_period IS NOT NULL AND direction = 'out')`. That is the entire fix at the constraint level: a dues reversal becomes the one shape of `kind='adjustment'` row allowed to carry a member and a period, and it must carry both, plus the row it reverses.
- A second CHECK guarding the column in the other direction: `CHECK (reverses_transaction_id IS NULL OR (kind = 'adjustment' AND direction = 'out' AND member_id IS NOT NULL AND dues_period IS NOT NULL))`. The disjunct above says a dues reversal *may* carry a member and a period; this says nothing that is not a dues reversal may claim to reverse anything. Both are needed, and the second is not defensive tidiness: without it a `kind='adjustment'` row could name a payment while carrying neither member nor period, and — worse — a `kind='normal'` row carrying no member and no period satisfies the dues CHECK unchanged and still sets the column. That row would hide the original payment from `DuesPaidByPeriod`, whose `NOT EXISTS` only asks whether *something* points at the row rather than whether a valid reversal does, and it would consume the reversed-once slot below so the genuine reversal could never be posted afterward. The ledger never writes such a row; the schema is what makes it unrepresentable, which is the standard ADR-024 already sets for every other column here.
- `UNIQUE (reverses_transaction_id) WHERE reverses_transaction_id IS NOT NULL` — a payment is reversible at most once, the same partial-unique shape as `reimbursement_settled_once`.
- A **composite** `FOREIGN KEY (fund_id, reverses_transaction_id) REFERENCES "transaction"(fund_id, id)`, not a single-column one. This is load-bearing, not house style for its own sake: every other pointer into `"transaction"` in this schema is composite for the reason ADR-024 already states — fund scoping — and a single-column FK here would let a treasurer of fund A name a row belonging to fund B as the payment they are reversing. It would be checked for existence and say nothing about ownership, so it would fail silently rather than loudly.
- `DuesPaidByPeriod` and `LatestDuesPeriodPaidByMember` each gain one `AND NOT EXISTS (SELECT 1 FROM "transaction" r WHERE r.reverses_transaction_id = t.id)` against the outer query's own row. Both already filter `WHERE kind = 'dues'`, so the reversal row itself — `kind='adjustment'` — was never going to surface in their scan; the clause instead drops the **original** dues row from the sum once something reverses it, which is what makes a reversed payment disappear from "paid" rather than simply appearing twice.
- `FundBalance`, `AccountBalance`, `PurposeBalance` — **no change**. They sum every direction regardless of `kind`, so a `direction='out'` row already subtracts correctly whatever its `kind` is. The bug this ADR fixes was never in the money; it was in the status derived alongside it.
- `Ledger.ReverseDuesPayment(ctx, ReverseDuesPaymentParams{FundID, TransactionID, OccurredOn, Note})`, one `withTx`: fetch the original row fund-scoped, then a single insert copying the five fields named above. Named errors for "no such transaction", "not a dues payment" (the target's `kind` isn't `'dues'` — which also rules out reversing a reversal), and "already reversed" — the last answering the partial unique index with a clean message rather than a raw constraint string, the shape [ADR-027](./027-ledger-domain-boundary.md) already uses for `ErrReimbursementAlreadySettled`.

**Why not net the reversal into the original kind.** The design going into the grill was signed netting: post the reversal as `kind='dues', direction='out'` and let it fall into `DuesPaidByPeriod`'s existing `SUM(amount)`, no new column, no new CHECK disjunct. It lost for one reason sharp enough to settle the question alone. `LatestDuesPeriodPaidByMember` is `SELECT member_id, MAX(dues_period) ... WHERE kind = 'dues' GROUP BY member_id` — it carries no notion of direction at all, because nothing before this needed one. Under netting, a period whose net reaches zero is still the chronological **maximum** `dues_period` value any `kind='dues'` row names for that member. A member who genuinely paid March, then had a wrongly-entered June payment reversed, would read as paid **through June** — paid in advance, off a period that is no longer paid at all — a new trust-core bug in the very derived value #82 exists to fix, and one the netting sketch never named. Excluding the reversed row from `kind='dues'` scans by construction — by giving it a different `kind` entirely — avoids the class rather than patching around it.

Netting would also have flipped `TestDuesFieldsBelongToDuesAndNothingElse`'s existing `"dues paid outward"` case from an asserted CHECK violation to something the schema must now accept, inverting a named, green guarantee to make room for the new behavior. Under the chosen design no existing dues test changes meaning: the new CHECK disjunct is vacuous for every row already in the suite, and every existing dues test predates any reversal, so the new `NOT EXISTS` clause holds vacuously against all of them.

Two narrower shapes were considered and dropped without much argument. A `dues_void`-style third `kind` value needs the same CHECK relaxation *and* a new enum member for behavior `adjustment` already names. A generic reverse-any-transaction primitive is wider than PRD §4 asks Uruni to be — the CHECK, the method, and the eventual endpoint stay exactly as wide as dues.

## Consequences

**Full-reversal-only.** There is no one-tap "reassign this payment to the right member" — the wrong-member case costs two postings, reverse then re-post against the right member, not one. This is deliberate, and now recorded in PRD §7.3 and §11 (merged in [#99](https://github.com/kerti/uruni/issues/99)): nothing else in Uruni lets a posted purpose or account be reassigned either, and a reassignment primitive would be the first place a posted fact is edited rather than superseded. Revisitable later as its own scoped decision if the wrong-member case turns out to dominate real use — not by reopening this one.

**A schema edit inside [ADR-025](./025-one-migration-file-until-1.0.md)'s one-file regime.** `reverses_transaction_id`, its CHECK disjunct, its partial unique index, and its composite FK all land in `00001_schema.sql`, edited in place — not a second migration file. Whoever implements this runs `make db-reset` afterward, not `make migrate-up`: goose has already recorded the one file as applied and cannot see that its content changed underneath it.

**#82 and #96 read as one CHECK problem and are not.** #96 needed no schema change at all — a transaction-boundary bug, fixed entirely in Go, already merged. This ADR is the schema-touching half; the two should be reviewed for what each actually changed, not folded into a single "dues CHECK" story after the fact.
