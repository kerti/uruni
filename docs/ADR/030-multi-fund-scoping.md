# ADR-030 — Multi-fund scoping: implicit fund resolution, single-account authorization

**Status:** Accepted · `draft` — no code implements this yet, so it may still be edited in place · [ADR index](./README.md)

**Context.** PRD §6 sanctions more than one fund per server: *"One community server holds one or more Funds (for the validated user, a single shared fund is enough; the model allows more without UI complexity)."* The schema already agrees — every domain table carries `fund_id` under a composite `UNIQUE (fund_id, id)` so a child cannot reference another fund's row ([ADR-024](./024-schema-conventions.md)), and #70 made the last unscoped single-row reads (`GetIncidental` ×2, `GetReimbursement`) fund-scoped with ledger tests proving a second fund's rows are invisible across the boundary. The model is ready. The API is not: `resolveFund` (`internal/http/setup.go`) calls `ListFunds` and returns `funds[0]`, or 404 "run setup" — 29 call sites across 13 handler files funnel through it, and no middleware, context value, or query/path parameter for a fund exists anywhere. `ErrFundAlreadyExists` is the only thing keeping v1 to one fund, and it is deliberately an application-level refusal, not a `CHECK` or `UNIQUE` index — chosen 2026-08-13 (`Decisions.md`) precisely so the policy could be lifted without a migration if the policy ever changes.

No auth exists yet: no session/user table, no user↔fund relation, `internal/http/middleware.go` is request-logging only. [ADR-007](./007-auth-local-email-password.md) is itself still `draft` and says only "local auth ... effectively one user" — it never addresses what a session should know about a fund, because until now nothing needed a fund concept at the request layer at all. M5 is the first slice that introduces a person who logs in, so it is the first slice that can get the relationship between identity and fund wrong, and the only slice where getting it right costs nothing extra. The SPA gives this decision a clean run at it: `web/src/App.tsx` has exactly one `fetch('/healthz')` and no API client, so neither routing scheme this ADR could pick has any existing frontend cost to unwind.

## Decision

**1. A JSON API request does not name its fund — resolution stays server-side and implicit.** No `/api/funds/{id}/...` prefix. `resolveFund` keeps its current job through v1: return the one fund `ListFunds` finds, 404 "run setup" if none. Rejected: prefixing the URL now, to get fund-awareness "for free" before a second fund or a client exists to exercise it. It buys nothing PRD §6 asks for — the validated user needs exactly one fund — and it costs the 29 handler call sites and roughly 80 request-URL literals across 16 handler test files a read-only survey counted, plus baking a `{fundID}` segment carrying one legal value into every fetch call the M6 SPA will ever write. The cost is not avoided, only deferred: whenever a second fund is real, whatever resolves "the fund" for a request still has to learn to choose one, and every one of those call sites still has to change. This decision pays that cost once, later, instead of once, now, for nothing.

**The public report is the deliberate exception, and it is scoped to `/api` for that reason.** M7's `/report/{slug}` does name its fund, because `report_slug` *is* a fund handle in the path (`router.go` reserves the prefix; the schema makes the slug globally `UNIQUE`). It has to: the report is unauthenticated by design (PRD §7.9, §8), so it has no session and no "the fund" to fall back on. Stating decision 1 without this carve-out would make it a claim M7 breaks on arrival. It also means fund-from-request is not, by then, an unpaid cost — the report will have proven the shape works here, which is a fair discount against the 29 sites and ~80 test literals above, though not enough to reverse the ruling: `/api` has a session and the report cannot have one. **The slug is a capability, not an authorization** — holding the link reads that fund's report, which is exactly PRD §7.9's intent, and it never becomes the fund selector for an authenticated route. That seam stays a public read handle.

**2. Authorization: a session proves the treasurer, not a fund.** PRD §8 is explicit that local auth is "for the single treasurer in v1." M5's session/user row must not carry a `fund_id`, and M5 must not introduce a user↔fund membership table. "Authenticated" means "you are this instance's treasurer" and nothing more; which fund that grants writes to remains whatever `ErrFundAlreadyExists` and `resolveFund` already decide, untouched by login. **Bootstrap: registration comes first, and it is one-shot.** With no user↔fund relation, the account and the fund are created by two independent acts, and the first of them runs with nobody authenticated — so one door is open on a fresh instance and the ADR has to say which. It is registration: `POST /register` precedes `POST /setup`, and refuses the moment **any** account exists, the same shape `ErrFundAlreadyExists` already has inside `SetUpFund` (`internal/ledger/setup.go`). The refusal is keyed to the count, not to a duplicate identifier — a uniqueness collision on the email is worth keeping for its own sake, but it is not the gate: the second stranger to reach a fresh instance registers with a *different* address and sails past it, and `resolveFund` would then hand that account `funds[0]` with full write access. One account per instance, one fund per instance, both locked after first use. The mapping from that account to that fund is therefore derivable and is not stored: a `user.fund_id` column would write down a fact that is already true, in exchange for the door this ADR is trying to keep shut. The accepted cost is password recovery — with one account and no member contact data (PRD §8), a forgotten password is recovered by the host at the database or by a CLI reset, not by self-service. 

This is the ruling that actually has to land before M5's slices are planned: a `user.fund_id` column or an early membership table would wire "one identity, one fund" into the schema and the auth middleware before anything requires it, and that assumption is far more expensive to unwind once real sessions and a real treasurer's cookies depend on it than it is to simply not build in the first place. Building the honest, narrower thing costs the same today as building the presumptive one; the difference only appears at the moment it has to be undone.

**3. Where it stops: v1 never renders a second fund; scoping stays defensive.** No fund switcher, no fund list, no fund-related setting. PRD §6's "the model allows more without UI complexity" is load-bearing, not decorative — the schema already proves the model *can* (ADR-024's composite FKs, #70's tests), so the API and UI are free to go on behaving as if there is exactly one fund, because there is, by policy, exactly one. This is not a screen deferred for lack of time; it is a screen PRD §4 does not ask for, and `CLAUDE.md`'s prime directive says to decline that, not design it in defensively.

**Reversible, not a one-way door — but not free, either.** The data model needs no migration to carry a second fund: every table already scopes by `fund_id`, and `ErrFundAlreadyExists` is one unindexed `if` inside `SetUpFund` — removing it is a one-line change, by design (`Decisions.md`, 2026-08-13). What this ADR genuinely defers, and what will cost real work when it is undone: giving `resolveFund` (or whatever replaces it) an actual selection mechanism instead of "the only row" touches the same ~29 handler sites and ~80 test literals a URL prefix would touch today; and a real per-fund authorization model — which account may act on which fund — does not exist in any form yet and has to be designed then, not merely wired. Getting decision **2** wrong now is the one true one-way risk here: a schema column is cheap to add and drop pre-`v1.0.0` ([ADR-025](./025-one-migration-file-until-1.0.md)), but a session and middleware model built around "one identity ⇒ one fund" is a design assumption threaded through every authenticated handler, and redesigning that under a live treasurer's data is a materially worse rewrite than deciding correctly here, before either exists. And the cheapness itself expires: ADR-025's edit-in-place migration ends at `v1.0.0` by definition, so the relation this ADR declines to build is free to add only while no treasurer has data underneath it. Before the tag, reversing costs a column and the call sites; after it, a real migration against live money as well.

**What this defers, named.** The case is not hypothetical and deserves to be written down rather than implied: two treasurers, two funds, one instance — one person keeping a community's kas while another keeps a work unit's, neither able to see the other's ledger ([#110](https://github.com/kerti/uruni/issues/110)). That is multi-tenancy, and it is strictly more than [#79](https://github.com/kerti/uruni/issues/79)'s one-treasurer-several-funds: #79 needs fund *selection*, this needs fund *authorization* on every read and write. Both stay out through `v1.0.0`. What forbids them is not a §4 non-goal — that bullet is about members not having logins — but PRD §8's "local auth for the single treasurer in v1" and the prime directive. Until a pilot produces a treasurer who needs otherwise, the answer is a second instance: SQLite and a single binary make another compose project nearly free, and a fault in one cannot reach the other community's money.

## Consequences

M5 builds one local account per server instance and sessions that carry no fund identity beyond what `resolveFund` already resolves. `resolveFund` and its 29 call sites are untouched by this ADR — M5 wraps them behind auth middleware; it does not change what they resolve or add a parameter to them.

**What stays outside the gate: `GET /healthz`, `/report/{slug}`, `POST /register`, `POST /login`.** Nothing else. `POST /setup` is *inside* it, which is the one placement worth stating outright, because the opposite reads as obvious and is wrong: registration closes after first use, but between the treasurer registering and her finishing setup there is a window in which a public `/setup` lets a stranger create and name her fund — and `ErrFundAlreadyExists` would then make that permanent, `report_slug` and all. `POST /login` carries ADR-007's rate limiting; it is the only unauthenticated door left standing once registration has closed. `POST /logout` sits inside the gate but stays idempotent — destroy the session if there is one, clear the cookie, answer 204 either way, since a caller whose cookie already expired wants exactly what they are asking for. M5 also owes the SPA a session-check route (`GET /api/session`): cookies are httpOnly, so a booting client cannot tell whether it is logged in, nor whether setup has run, without asking — its payload is M5's to design, not this ADR's. One consequence of the gate is that `resolveFund`'s 404 "No fund has been set up yet" stops being readable by strangers and becomes a 401, which is the right answer and removes an existence oracle nobody chose to expose.

Lifting `ErrFundAlreadyExists`, giving fund resolution a real selection mechanism, and designing per-fund authorization are out of scope for every milestone on the current roadmap and stay that way absent a validated need for a second fund, per PRD §4's non-goals and `CLAUDE.md`'s prime directive. This ADR is what a future ADR supersedes if that need becomes real; until then it is the seam PRD §6 describes, left alone on purpose. Because the cheap window shuts at `v1.0.0`, #110 and #79 get an explicit yes-or-no from what the pilot at `v0.6.x` actually showed **before** that tag is pushed — the answer may well still be no, but it should be a decision rather than a silence.
