# ADR-031 — A closed envelope refuses postings, and reopening is the way back

**Status:** Accepted · `draft` — supersedes [ADR-027](./027-ledger-domain-boundary.md) on two points, named below · [ADR index](./README.md)

**Context.** [ADR-027](./027-ledger-domain-boundary.md) describes closing an incidental and, in the same paragraph, records the consequence it accepted: *"the purpose it closes stays open to new postings even afterward, so the check is the entire guarantee rather than a pre-check ahead of something the schema also enforces."* That was a knowing decision, not an oversight. [#152](https://github.com/kerti/uruni/issues/152) put an incidentals screen in the everyday loop and made the consequence reachable: the record form's purpose picker lists closed envelopes, because `purposeResponse` is `{id, kind, name}` with no lifecycle, and `PostTransaction` validates amount, direction and date and then inserts. Filed as [#214](https://github.com/kerti/uruni/issues/214), grilled 2026-09-09.

What that costs is not what it first appears. `CloseIncidentalAndRoll` rolls the leftover so the envelope's purpose balance is zero — `internal/http/balances_test.go` asserts exactly that — and closing is once-only (`ErrIncidentalAlreadyClosed`): there is no second roll and no reopen. A posting afterwards therefore makes the purpose balance permanently non-zero, in a purpose no screen surfaces, while the fund total still counts the money. Reconciliation cannot catch it, because it compares *accounts* against counted cash: the money is still in the box, so the fund reads "cocok" while the purpose split is wrong. That is the quiet class of error `CLAUDE.md` rule 2 and PRD §5 exist to rule out.

**It is not, however, double-spending, and an early framing of this issue said it was.** Every posting moves real money exactly once and the fund total stays honest in every case. The defect is attribution — which purpose the money is recorded against — not arithmetic. Naming it correctly matters, because the fix that double-spending would demand (refuse outright, always) is stricter than the one attribution needs.

**The maintainer's ruling is that flexibility belongs here**: a contribution that genuinely arrived before the close, recorded after it, is a real situation, and Uruni's premise is a calm experience with the least stress. This ADR is how that ruling survives contact with the ledger.

## Decision

**A closed envelope refuses every posting; reopening it is a deliberate, visible act; and closing always squares the envelope to zero.**

- **The guard.** `Ledger.PostTransaction` gains one business-state check in the shape of the three it already has: if `PurposeID` names an incidental whose `closed_on IS NOT NULL`, refuse with `ErrIncidentalClosed`, mapped to `409 incidental_closed` beside `incidental_already_closed`. One query — `SELECT closed_on FROM incidental WHERE purpose_id = ?` — which returns zero rows for `main` and `pass_through` purposes, so no `purpose.kind` branch is needed. This is a read-before-write business-state refusal, exactly the surface [ADR-027](./027-ledger-domain-boundary.md) says this package may expose; it is not a widening of `PostTransaction` into a second write shape.

- **The refusal is symmetric.** Both directions, not "in" only. A late bill for the occasion deserves attribution to the occasion as much as a late contribution does, and a direction-dependent rule would need an explanation for why an envelope may receive but not spend that neither PRD §7.5 nor the ledger supplies.

- **The way back is `POST /api/incidentals/{purposeID}/reopen`** — `closed_on` back to `NULL`, fund-scoped through the same join `GetIncidental` uses, with `ErrIncidentalNotClosed` for an envelope that is not closed. An action endpoint, matching the resource's own `.../close` idiom rather than the reimbursement resource's PATCH-a-nullable-field shape; one resource should not speak both. The treasurer reopens, posts the late entry through the ordinary record form with no special path, and closes again.

- **Closing rolls in whichever direction squares the envelope.** This supersedes ADR-027's second point. Today a negative leftover — an envelope that disbursed more than it collected — closes and posts nothing. Under this ADR: leftover positive rolls out to the main purpose as before; leftover **negative rolls in from the main purpose**, covering the shortfall; leftover zero still posts nothing. The invariant becomes single and testable: **a closed envelope's purpose balance is exactly zero, always.** Without this half, symmetry is unsafe — a late `out` would leave an envelope reading −20.000 forever, and M7's report would show a closed collection with a negative balance.

- **No new arithmetic is needed for the second close.** `IncidentalTotals` sums every row against the purpose with no `kind` filter, so the first roll's own `out` leg already counts toward `disbursed_amount` and the leftover after a close is 0 by construction. Reopening, posting, and re-closing therefore computes the *net delta* and rolls only that, through `CloseIncidentalAndRoll` otherwise unchanged. (That the same unfiltered sum misreports the rollover as money spent, on the detail screen, is a separate defect — [#215](https://github.com/kerti/uruni/issues/215) — and any fix there must preserve this property.)

- **`AccountID` keeps its existing meaning and needs no sibling.** It is the account both legs post through, and [ADR-027](./027-ledger-domain-boundary.md)'s reasoning for why its choice is immaterial to correctness — a same-account pair always nets to zero on that account — is direction-agnostic and holds unchanged when the pair runs main → envelope. There is no "where does the covering money come from" to answer: the pair changes what money is *for*, never where it sits. The close form's label must stop saying `Sisa dana masuk ke`, which is true in only one direction.

- **`rolled_amount` becomes signed.** Positive: leftover rolled into Kas Utama. Negative: a shortfall covered from Kas Utama. Zero: the envelope landed square. The existing "shown honestly, including zero" readout gains a second sentence rather than a second field.

- **The everyday picker stops offering what it cannot accept.** `GET /api/purposes?selectable=true`, filtered server-side. Not a `closed_on` field added to `purposeResponse`: that leaks an envelope's lifecycle into a shape every consumer reads, to serve one caller. The reopen flow, not the picker, is where the exception lives — without it the filter and the ruling would contradict each other, and a late entry would have no surface to happen on.

**Backdating needs nothing.** `occurred_on` stays free, and a late entry dated either side of `closed_on` is treated identically. [ADR-024](./024-schema-conventions.md) already settles why: `through_transaction_id` is an **id** cutoff, not a date, so *"a backdated correcting entry gets a higher id, so it lands outside the old snapshot's math and inside the live balance the next one compares against."* Date-aware validation here would be new special-casing for a problem the schema solved generically.

**No schema change.** `incidental.closed_on` already exists, already nullable, and `incidental` is — per ADR-027 — the one table M2 deliberately left without an immutability trigger, *"precisely because closing a collection moves no money and is a decision that gets revised."* Reopening is that revision, and the ADR being superseded is the one that anticipated it.

## Consequences

**The main purpose may go negative, and Uruni says so and stops there.** Covering a shortfall from a thin Kas Utama drives it below zero. That is true — the fund really did spend money it had not collected — and refusing it would be a new overdraft rule applied in exactly one place, when every other posting path in the app already permits an `out` larger than any balance.

**What it will not do is guess who fronted the money.** A negative purpose often means someone paid out of pocket, and the app does not record that on their behalf: `reimbursement.member_id` is `NOT NULL`, so an inferred reimbursement would have to invent *which member* is owed. The money could be the treasurer's cash, a member paying a vendor directly, or a contribution arriving next week. The treasurer resolves it with the mechanisms that already exist — a reimbursement she creates naming the actual person, or a transfer. Stating a liability nobody asserted is the same error as generating a note nobody wrote.

**This depends on the negative balance being visible, and today it is not.** `GET /api/balances` returns per-purpose balances, but nothing in the SPA renders one — `Home.tsx` uses them only as a name lookup for recent activity. Until purpose balances surface somewhere, "the treasurer deals with it" asks her to act on something she cannot see. Where they belong is the information-architecture question in [#212](https://github.com/kerti/uruni/issues/212), not a widget bolted onto this work.

**A reopened envelope rejoins the open list and the everyday picker.** That is better than the state this ADR fixes — the money is back where the treasurer already looks — but a reopen left unclosed is a new way to be untidy. The reopen flow should lead into the close form rather than leaving a bare toggle.

**Two sentinels, one endpoint, no new concept.** `ErrIncidentalClosed`, `ErrIncidentalNotClosed`, `POST .../reopen`, one query, one small affordance on a screen that already exists. Nothing a self-hoster runs, backs up or configures.

**Superseded in ADR-027:** the sentence accepting that a closed purpose *"stays open to new postings even afterward"*, and the negative-leftover branch that *"closes it and posts nothing"*. Both are stated there as deliberate, and both stop being true when this ADR's code lands — not before. So ADR-027 is marked superseded on those two points **in the PR that implements this**, in the strikethrough-and-pointer shape [ADR-018](./018-release-and-versioning.md) already uses for its migrations line, and not while this ADR is still `draft`: marking it earlier would have the index claim something about the code that is not yet so. That PR is also where this ADR's own `draft` tag comes off, since one slice implements it end to end.
