# ADR-007 — Auth: local email/password now, OIDC later

**Status:** Accepted · implemented at M5 — change only by adding a superseding ADR · [ADR index](./README.md)

**Decision.** **Local auth** — email/password hashed with **argon2id** (`golang.org/x/crypto/argon2`), server-side sessions with httpOnly secure cookies. OIDC is an additive option later (`coreos/go-oidc`).

**The session library is [alexedwards/scs](https://github.com/alexedwards/scs), and the open choice this ADR used to carry — "or a minimal hand-rolled store given it's effectively one user" — is closed against it.** That parenthetical read as licence to skip a dependency, but the risk it was hedging is session fixation, non-constant-time token comparison and cookie-flag mistakes: precisely the class `CLAUDE.md` routes to `builder-deep` rather than to a quick afternoon. A small, single-purpose MIT library is not a framework. Trading a few hundred lines of untested cookie-security code for one well-exercised dependency is rule 7 honoured, not bent. **Storage is our own `Store` over sqlc** (`internal/http/session_store.go`), never scs's bundled `sqlite3store`: that package's hand-written SQL would sit outside [ADR-005](./005-data-access-sqlc.md)'s reviewed-SQL discipline, where every query is checked in beside the schema.

**The surface is four routes, and three of them stay unauthenticated.** `POST /api/register` (one-shot bootstrap, and it logs the treasurer straight in), `POST /api/login`, `GET /api/session` (`{authenticated, has_account}` and nothing else), `POST /api/logout` (204 whether or not a session was there). Everything else under `/api` is behind the session gate, **`POST /setup` included**. Authorization and bootstrap are [ADR-030](./030-multi-fund-scoping.md)'s ruling, not this ADR's: a session proves the treasurer and carries no fund. See it for why `/setup` is inside the gate and why `has_account` is an existence oracle chosen rather than overlooked.

**Why.** Zero external setup for the host; the public report page (7.9) is unauthenticated, so login only guards the treasurer's writes.

**Consequences.** Ship secure defaults:

- **Login rate limiting**, in-process and in-memory, fixed-window, keyed independently by client IP and by submitted identifier — both live at once, so a distributed guesser and a single-account brute force are each caught by the key the other evades. In-process is the honest shape for one binary and one account; nothing here wants a Redis.
- **Cookie flags:** `HttpOnly`, `SameSite=Lax`, and `Secure` derived from `URUNI_BASE_URL`'s scheme rather than from a config flag of its own — https means the operator has a real TLS origin in front (Caddy, [ADR-009](./009-reverse-proxy-caddy.md)); plain-HTTP loopback is `make web-dev`, where a Secure cookie would simply never be sent and login would look broken with no error to explain it.
- **No separate CSRF token, and that is a decision rather than an omission.** Single origin, a JSON API, and `SameSite=Lax` between them mean no cross-site context attaches the cookie to a state-changing POST. Lax stops at the site boundary, though: a page on a sibling subdomain of the same registrable domain is same-site and still gets the cookie. So every non-safe request under `/api` from another origin is also refused before the session loads (`crossOriginGuard`, Go's `http.CrossOriginProtection`: `Sec-Fetch-Site`, falling back to `Origin` against `Host`). That check is stateless. A token would add a round trip and a failure mode to defend a seam these two already close. If a cross-origin client is ever real, that reopens here.
- HTTPS-only via Caddy.

## Amendments

An amendment corrects a statement of fact about the code that has since become false. It never changes a decision, a trade-off or an accepted cost. Those still need a superseding ADR. See the [ADR index](./README.md) for the rule.

**2026-10-08 ([#481](https://github.com/kerti/uruni/issues/481))**: the *No separate CSRF token* bullet named `SameSite=Lax` as the whole defence. It read: "Single origin, a JSON API, and `SameSite=Lax` between them mean no cross-site context attaches the cookie to a state-changing POST. A token would add a round trip and a failure mode to defend a seam that is already closed." That stays true for cross-site requests, but the #447 security pass found that a same-site page still gets a Lax cookie. #481 added a cross-origin check on `/api` writes. The decision against a token is unchanged.

**2026-10-13 ([#495](https://github.com/kerti/uruni/issues/495), [#500](https://github.com/kerti/uruni/issues/500))**: the *Login rate limiting* bullet read: "in-process and in-memory, fixed-window, keyed independently by client IP and by submitted identifier - both live at once, so a distributed guesser and a single-account brute force are each caught by the key the other evades." That no longer describes the code. The limiter stays in-process and in-memory, and counts an attempt before the work it guards starts (#495), so concurrent guesses are counted while still in flight. It guards three routes: login, restore confirm (sharing the login limiter) and register (its own limiter, per client network). Password hashing and verifying run behind a process-wide gate, and a request that cannot get a slot is answered `503 server_busy` and is not counted as a guess. Since #500, login is keyed by client network (the full address for IPv4, the /64 for IPv6, IPv4-mapped IPv6 as IPv4), by the normalised email together with that network, and by the normalised email alone as a looser flat ceiling of 50 attempts an hour. A key that fills its 10-attempt window is locked for 5 minutes, then 15, then 1 hour on repeats, the strikes decaying after a day without a lockout and clearing on a successful login. A successful login also gives the browser a device cookie (opaque random token, HttpOnly, SameSite=Lax, Secure on https, 30 days, only its hash kept in memory); a login that presents a valid cookie for the same email is counted on one key of its own, at the same limit and ladder, and not on the network or ceiling keys, so a stranger who fills those cannot lock the treasurer out of a browser she has used. Emails are trimmed and lower-cased at register, login and `create-user`, and looked up case-insensitively. The decision to rate-limit in-process, with no external store, is unchanged.
